It is noteworthy that the notation $\ov{E}$ denotes a possibly empty sequence of elements $E$ separated by commas apart from $\ov{\alpha\texttt{:}\,\TST}$, where it denotes a non-empty sequence.
Furthermore, not only is $\TSAn$ non-empty sequential elements but also multi-line elements unlike the other comma-separated sequences. That is TypeSpecs only allows one specification on one line.

This specification addresses the most fundamental and atomic types based on the TypeSpecs reference on Elixir documentation.
The addressed are, starting from the top type \texttt{any()} and the bottom type \texttt{none()}, controversially vague concept of field types of record types.
While thus enables expressing every existing TypeSpecs type, some might come up with questions on fundamentality with subtype relations or notion of expressions between basic types and literal types.
In the following sections, these questions are addressed for clarity with listing the built-in types and the syntactic sugars in Table~\ref{app:typespecs-builtin-types} and Table~\ref{app:typespecs-syntactic-sugars}.

\subsection{TypeSpecs Basic Types and Literals}
TypeSpecs is rather expressive especially by providing the literal types that are also used in the code with the same form.
However, this is classic that the higher expressiveness brings the higher complexity and TypeSpecs is not exempt.
The common trade-off must be discussed here due to the fact that our ultimate goal is to translate TypeSpecs to Elixir Types.
In the perspective of translation, while TypeSpecs allows literals types such as \texttt{:$k$}, \texttt{[]}, \texttt{<<>>}, \texttt{(\fun{$\ov{\TST}$}{\TST})} and \texttt{$n$..$n'$},
Elixir Types will not support \texttt{<<>>}, and the range type (i.e., \texttt{$n$..$\prm{n}$}) will not appear to users but will be only used internally.
This difference will not allow direct translations for all the types and eventually necessitate approximations of them in Elixir Types.

%1. :k ≤ atom() ?
The first question could arise is from the subtype relationship between \texttt{atom()} and \texttt{:$k$}.
It is true that \texttt{:$k$} is a subtype of \texttt{atom()} since \texttt{:$k$} represents every single atom type and \texttt{atom()} represents a set of all atom types.
Nonetheless, we have to contain \texttt{:$k$} in the syntax specification.
That is because \texttt{:$k$} is a literal type that could be any single atom type, e.g., \texttt{:true} and \texttt{:false} are literals that are used as themselves in the code and also in type specification.
Therefore, it is always sound for \texttt{atom()} to replace \texttt{:true} or \texttt{:false} but not vice versa.


%2. neg_integer(), non_neg_integer(), pos_integer() and ".."
It could be viewed that the range literal (i.e., \texttt{$n$..$\prm{n}$}) expresses \texttt{neg\_integer()}, \texttt{non\_neg\_integer()} and \texttt{pos\_integer()}.
This idea could be backed by Types and Their Syntax in Erlang documentation that these are built-in types which can be thought defined by \texttt{..-1}, \texttt{0..} and \texttt{1..}, respectively.
But Elixir documentation specifies them as basic types and the provided range syntax in Erlang documentation is not correct use.
Provided, it is sufficient to say that these are not subtypes of \texttt{$n$..$\prm{n}$}, hence they are necessary to be in the syntax specification.

\subsection{Translation of Fields}

Let $\tau$ range over the right-hand side type of field types, that is, $\tau$ is either $\TST$ or $\ifset\TST$. We consider lists whose elements are of the form \texttt{\ETK\,\,=>\,\,$\tau$}. Given such a list $L$ we write $\ETK\in L$ is there exist $\tau$ such that the element \texttt{\ETK\,\,=>\,\,$\tau$} belongs to $L$. We denote by \textsf{Empty} the lists that maps all the non-singleton key types to \texttt{not\_set()}.  

First we define the translation of single field types. If $\ETK_1,...,\ETK_n$ are pairwise distinct key types, we write \texttt{[$\bigvee_{i=1}^n \ETK_i\fto\tau$]} for the list \texttt{[$\ETK_1\fto\tau,\cdots,\ETK_n\fto\tau$]}. Then the translation of single field types is defined in Figure~\ref{app:translation-in-field-types}:

\begin{figure} [H]
   \begin{translationfig}
      \dsb{\texttt{required(\TST) => $\prm{\TST}$}} = 
      \left\{
         \begin{array}{ll}
            \texttt{[\,:$k$\,\,=>\,\,$\dsb{\prm{\TST}}$\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\texttt{:}k
            \nl
            \texttt{[\,}\bigvee_{i \in I}\ETK_i\fto\ifset{\dsb{\prm{\TST}}}\texttt{\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\bigvee_{i \in I}\ETK_i\textsl{\,\,and\,\,}\dsb{\TST}\,\not\approx\,\texttt{:}k %(\ETK_i\text{'s are pairwise distinct}) 
            \nl
            \textsl{undefined} & \textsl{otherwise}
         \end{array}
      \right.
      \nl \nl
      \dsb{\texttt{optional(\TST) => $\prm{\TST}$}} = 
      \left\{
         \begin{array}{ll}
            \texttt{[\,}\bigvee_{i \in I}\ETK_i\fto\ifset{\dsb{\prm{\TST}}}\texttt{\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\bigvee_{i \in I}\ETK_i
            \nl
            \textsl{undefined} & \textsl{otherwise}
         \end{array}
      \right.
   \end{translationfig}
   \\[4mm] where all $\ETK_i$'s in $I$ are pairwise distinct.
   \caption{Translation in Field Types}
   \label{app:translation-in-field-types}
\end{figure}

After obtaining types in Elixir Types we can define merge function. Given two field lists $L_1$ and $L_2$, we write $L_1 \oplus L_2$ the list obtained by adding to $L_1$ all the fields elements $\ETK\fto\tau$ of $L_2$ such that $\ETK\not\in L_1$ and $\ETK\neq\texttt{:}k$. Formally:
\begin{figure} [H]
   \[\begin{array}{rcll}
      L_1 \oplus \texttt{[\,]} &= & L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau,\,\,L_2\,\texttt{]} &=& L_1 \oplus L_2 & \textsl{if }\ \ETK\in L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau,\,\,L_2\,\texttt{]} &=& \texttt{[}\,\ETK\fto\tau,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ \ETK\not\in L_1 \\
      L_1 \oplus L_2 &=& \textsl{undefined} & \textsl{otherwise}
      \end{array}\]
   \caption{Merge in Field Types}
   \label{app:merge-in-field-types}
\end{figure}

Notice that merging naturally reverses the order of field types, that is because field types in TypeSpecs are left-associative whereas those in Elixir Types are right-associative.

We then finally define \textsf{map($L$)} as the map type whose field list is $L$. Then we have $\dsb{\map{\texttt{\TSF$_1$,\,...,\,\TSF$_n$}}} =\textsf{\textsl{map}($\bigoplus_{i=1}^{n}\dsb{\TSF_i}$)}$. If we want a saturated map type (i.e., a map type that specifies all the possible key types), then we have $\dsb{\map{\texttt{\TSF$_1$,\,...,\,\TSF$_n$}}} =\textsf{\textsl{map}($\bigoplus_{i=1}^{n}\dsb{\TSF_i}\oplus\texttt{Empty}$)}$.

In spite of the whole translation process we have completed, there are two missing parts to be complemented: merging of field types with their left-hand side undefined and that being a singleton atom type.
While the former is naturally agreed to have no direct translation hence requires approximation, one might argue that the latter should be fully addressed in the translation part.
This argument is solid and true, but we are passing this matter to the approximation.
That is because the both to-be-dealt cases share the common ground that they are literal types or else called singleton types.
Therefore, it is easier and more efficient to treat them in the same manner as subtypes except the fact that \texttt{:$k$} will eventually appear in fields as it is one of the actual key types of Elixir Types.


\section{Total Approximating Translation of TypeSpecs into Elixir Types}

The translation defined so far is partial since some TypeSpecs types do not have a corresponding type in Elixir Types. 
This is not a weakness of the Elixir Types system, but rather a consequence of the design choices made for Elixir Types, to keep them as simple as possible while still being useful. 
However, it is possible to define a total translation from types in TypeSpecs to ones in Elixir Types hence approximating the original types in TypeSpecs. 
This total translation can be useful in some contexts, for example, when we want to ensure that every type in TypeSpecs can be represented in Elixir Types even approximately.

More precisely, the previous translations are undefined in the following cases:
\begin{itemize}
   % \item Bitstrings with size specifications that are not a multiple of 8 bits (e.g., \texttt{<<\_::3>>}).
   \item $\dsb{\texttt{(\fun{\dots}{\TST})}}$: 
   the top function type when $\dsb{\TST}$ is not equivalent to \texttt{any()}.
   \item $\dsb{\texttt{required(\TST) => $\prm{\TST}$}}$ and $\dsb{\texttt{optional(\TST) => $\prm{\TST}$}}$: 
   the field types when $\dsb{\TST}$ is equivalent to a singleton atom type or is not equivalent to a disjunction of pairwise distinct key types.
\end{itemize}
In the rest of this section we give a conservative extension of the translation defined so far that is total, i.e., it is defined for every type in TypeSpecs. 
The extension consists in defining approximations for the cases where the previous translation is undefined.

\subsection{Approximation of Top Function Types}

The top function type is a set of all the possible functions, that is, unions of functions returning the top type with every arity available as defined in Figure~\ref{app:top-function-type}.

\begin{figure} [H]
   \[\begin{array}{rcll}
         \texttt{\fun{\dots}{any()}} \equiv \texttt{\fun{none()}{any()}\,\,$|$\,\,\dots\,\,$|$\,\,\fun{($\underbrace{\texttt{none(), \dots, none()}}_{255\text{  times}}$)}{any()}}
   \end{array}\]
   \caption{Top Function Type}
   \label{app:top-function-type}
\end{figure}

Elixir Types provides the semantically same type, \texttt{fun()}, which enables the direct translation for \texttt{\fun{\dots}{any()}},
although, Elixir Types does not directly define \texttt{fun()} as Figure~\ref{app:top-function-type}, due to the triviality of defining the list of functions with all the possible arity, and the cost of defining and having all the function types which expand to maximum arity of 255.
Nonetheless, the fundamental difference in allowance from TypeSpecs, i.e., letting to specify the codomain of a function type, brings subtypes of the top function type on approximation.

The approximation is rather simple because the leniency in expressiveness is proven to be trivial in practice for several reasons.
Most of all, Dialyzer does not differentiate the return type and perceive any form of the top types as \texttt{\fun{\dots}{any()}}.
Which means, in TypeSpecs with Dialyzer, \texttt{\fun{\dots}{any()}} can replace any other top type functions with a codomain different than \texttt{any()} and the same applies to the other way around.
Secondly, one of the concerns with moving forward with Elixir Types is to fail typecheck, but typecheck will trivially succeed even alone with \texttt{fun()} when approximated since the top function type already takes over all the other function types.
One small problem is that this approximation will blunt the specification, hence we can write \texttt{fun() and dynamic()}, which is a subtype of \texttt{fun()}, to semantically display that the approximation is a subtype of the top function type.

\begin{figure} [H]
   \begin{translationfig}
      \dsb{\texttt{(\fun{\dots}{\TST})}} \approx
      \left\{
         \begin{array}{ll}
            \texttt{fun()} & \textsl{if}\,\,\,\,\dsb{\TST}\,\approx\,\texttt{term()}
            \nl
            \texttt{fun() and dynamic()} & \textsl{otherwise}
         \end{array}
      \right.
   \end{translationfig}
   \caption{Approximation of Top Function Type}
   \label{app:approximation-of-top-function-type}
\end{figure}

\subsection{Approximation of Field Types}

Let us deal with the merging case when left-hand sides of two field types are not disjoint.
This also involves the case when a required key type in TypeSpecs is translated into \texttt{:$k$} since it is one of the literal types that are subtypes of key types of Elixir Types.
To define the approximation, let $s$ ranges over all the singleton types and let $S$ to be $\bigcup_{i\in I}s_i$ which represents any set of unions of singleton types or simply a key type in Elixir Types.
In extension to the merge function in Figure~\ref{app:merge-in-field-types}:

\begin{figure} [H]
   \[\begin{array}{rcll}
      L_1 \oplus \texttt{[}\,s\fto\tau,\,\,L_2\texttt{]} &=& L_1 \oplus L_2 & \textsl{if }\ S \in L_1 \\
      L_1 \oplus \texttt{[}\,S\fto\tau,\,\,L_2 \texttt{]} &=& \texttt{[}\,S\texttt{ and not\,\,$s$}\fto\tau,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ \texttt{$s$} \in L_1 \\
      \end{array}\]
   \caption{Approximated Merge in Field Types}
   \label{app:approximated-merge-in-field-types}
\end{figure}

This works, for instance, when attempted merging a singleton atom type with \texttt{atom()} and vice versa.
Since a singleton atom type is a subtype of unions of all the atom types, if a field type with \texttt{:$k$} comes before the next field type with \texttt{atom()} at their left-hand sides, the former field does not fully take precedence over the latter field but only the single type that is itself.
On the other hand, if a field type with \texttt{atom()} comes before a \texttt{:$k$}, the former takes full-priority over the latter. 

Notwithstanding the fact that it all works on atom types, the second line of Figure~\ref{app:approximated-merge-in-field-types} is incompatible with other singleton types.
For example, translating \map{\texttt{1..3\,\,=>\,\,float(), integer()\,\,=>\,\,integer()}} requires approximated merge function, but with the definition in Figure~\ref{app:approximated-merge-in-field-types}, it results in \map{\texttt{integer() and not 1..3\,\,=>\,\,integer(), 1..3\,\,=>\,\,float()}}.
Which is invalid in Elixir Types. Therefore in addition to Figure~\ref{app:approximated-merge-in-field-types}:

\begin{figure} [H]
   \[\begin{array}{rcll}
      L_1 \oplus \texttt{[}\,S\fto\tau,\,\,L_2 \texttt{]} &=& \texttt{[}\,S\fto\tau \texttt{ or }\tau^s,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ s \in L_1 \\
      \end{array}\]
   \caption{Approximated Merge with Singleton Key Types}
   \label{app:approximated-merge-with-singleton-key-types}
\end{figure}

In the all cases, the best we can do is to over-approximate the singleton key types to their super types existing in key types, and then unify their value types with the proceeding field's value types instead of overwriting them.
Although this will lose the precision that singleton types provide, the advantage of this approximation is while achieving simplicity of the type system, it can also maintain its overall meaning and soundness.

Finally, let us consider the case no merge is required but the approximation is.
That is when the translation of each field yields undefined.
The best option here is still to over-approximate it to a key type of which the type is a subtype.
On top of that, we can intersect \texttt{dynamic()} to the over-approximated key type to semantically display its subtype nature.

Finally, we can write the total merge function with the approximation:

\begin{figure} [H]
   \[\begin{array}{rcll}
      L_1 \oplus \texttt{[\,]} &= & L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau,\,\,L_2\texttt{]} &=& L_1 \oplus L_2 & \textsl{if }\ \ETK\in L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau,\,\,L_2 \texttt{]} &=& \texttt{[}\,\ETK\fto\tau,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ \ETK\not\in L_1 \\
      L_1 \oplus \texttt{[}\,s\fto\tau,\,\,L_2\texttt{]} &=& L_1 \oplus L_2 & \textsl{if }\ S \in L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau,\,\,L_2 \texttt{]} &=& \texttt{[}\,\ETK\texttt{ and not\,\,:$k$}\fto\tau,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ \texttt{:$k$} \in L_1 \textsl{ and } \ETK = \texttt{atom()} \\
      L_1 \oplus \texttt{[}\,S\fto\tau,\,\,L_2 \texttt{]} &=& \texttt{[}\,S\fto\tau \texttt{ or }\tau^s,\,\,L_1\texttt{]}\oplus L_2  & \textsl{if }\ s \in L_1 \textsl{ and } s \neq \texttt{:$k$} \\
      \texttt{[}\, L_1,\,\,s\fto\tau,\,\,L_2\texttt{]} &=& \texttt{[}\, L_1,\,\,\ETK^s\texttt{ and dynamic()}\fto\tau,\,\,L_2\texttt{]} & \textsl{otherwise} \\
      \end{array}\]
   \caption{Total Merge in Field Types}
   \label{app:total-merge-in-field-types}
\end{figure}
