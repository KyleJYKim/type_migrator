\subsection{Translation of Fields}

Let $\tau$ range over the right-hand side type of field types, that is, $\tau$ is either $\TST$ or $\ifset\TST$. We consider lists whose elements are of the form \texttt{\ETK\,\,=>\,\,$\tau$}. Given such a list $L$ we write $\ETK\in L$ is there exist $\tau$ such that the element \texttt{\ETK\,\,=>\,\,$\tau$} belongs to $L$. We denote by \textsf{Empty} the lists that maps all the non-singleton keytypes to \texttt{not\_set()}.  

Given two field lists $L_1$ and $L_2$, we write $L_1 \oplus L_2$ the list obtained by adding to $L_1$ all the fields elements $\ETK\fto\tau$ of $L_2$ such that $\ETK\not\in L_1$. Formally:
\begin{figure} [H]
   \[\begin{array}{rcll}
      L_1 \oplus \texttt{[\,]} &= & L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau, L_2\texttt{]} &=& L_1 \oplus L_2 & \textsl{if }\ \ETK\in L_1 \\
      L_1 \oplus \texttt{[}\,\ETK\fto\tau, L_2 \texttt{]} &=& \texttt{[}\,\ETK\fto\tau, L_1\texttt{]}\oplus L_2  & \textsl{if }\ \ETK\not\in L_1 \\
   \end{array}\]
   \caption{Merge in Field Types}
   \label{app:merge-in-field-types}
\end{figure}
We then define \textsf{map($L$)} as the map type whose field list is $L$. Then we have 
$\dsb{\map{\texttt{\TSF$_1$,\,...,\,\TSF$_n$}}} =\textsf{\textsl{map}($\bigoplus_{i=1}^{n}\dsb{\TSF_i}$)}$. If we want a saturated map type (i.e., a map type that specifies all the possible keytypes), then we have $\dsb{\map{\texttt{\TSF$_1$,\,...,\,\TSF$_n$}}} =\textsf{\textsl{map}($\bigoplus_{i=1}^{n}\dsb{\TSF_i}\oplus\texttt{Empty}$)}$.

All it remains to do is to define the translation of field types. If $\ETK_1,...,\ETK_n$ are pairwise distinct key types, we write \texttt{[$\bigvee_{i=1}^n \ETK_i\fto\tau$]} for the list \texttt{[$\ETK_1\fto\tau,\cdots,\ETK_n\fto\tau$]}. Then the translation of single field types is defined in Figure~\ref{app:translation-in-field-types}.:
\begin{figure} [H]
   \begin{translationfig}
      \dsb{\texttt{required(\TST) => $\prm{\TST}$}} = 
      \left\{
         \begin{array}{ll}
            \texttt{[\,:$k$\,\,=>\,\,$\dsb{\prm{\TST}}$\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\texttt{:}k
            \nl
            \texttt{[\,}\bigvee_{i \in I}\ETK_i\fto\ifset{\dsb{\prm{\TST}}}\texttt{\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\bigvee_{i \in I}\ETK_i\textsl{\,\,and\,\,}\dsb{\TST}\,\not\approx\,\texttt{:}k %(\ETK_i\text{'s are pairwise distinct}) 
            \nl
            \textsl{undefined} & \textsl{otherwise}
         \end{array}
      \right.
      \nl \nl
      \dsb{\texttt{optional(\TST) => $\prm{\TST}$}} = 
      \left\{
         \begin{array}{ll}
            \texttt{[\,}\bigvee_{i \in I}\ETK_i\fto\ifset{\dsb{\prm{\TST}}}\texttt{\,]}
            & \textsl{if}\,\,\,\,\dsb{\TST}\,\,\approx\,\,\bigvee_{i \in I}\ETK_i
            \nl
            \textsl{undefined} & \textsl{otherwise}
         \end{array}
      \right.
   \end{translationfig}
   \\[4mm] where all $\ETK_i$'s in $I$ are pairwise distinct.
   \caption{Translation in Field Types}
   \label{app:translation-in-field-types}
\end{figure}

\section{Total Approximating Translation of TypeSpec into Elixir Types}

The translation defined so far is partial since some TypeSpec types do not have a corresponding Elixir type. This is not a weakness of the Elixir type system, but rather a consequence of the design choices made for Elixir types, to keep them as simple as possible while still being useful. However, it is possible to define a total translation from TypeSpec types to Elixir types that approximates the original TypeSpec type. This total translation can be useful in some contexts, for example when we want to ensure that every TypeSpec type can be represented in Elixir types, even if approximately.

More precisely, the previous translation is undefined in the following cases:
\begin{itemize}
   \item Bitstrings with size specifications that are not a multiple of 8 bits (e.g., \texttt{<<\_::3>>}).
   \item The type \texttt{\fun{\dots}{\TST}} when the translation of $\TST$ is not equivalent to \texttt{any()} (explain why this type is not interesting).
   \item .... (n..n)
   \item $\dsb{\texttt{required(\TST) => $\prm{\TST}$}}$ and $\dsb{\texttt{optional(\TST) => $\prm{\TST}$}}$ are undefined when $\dsb{\TST}$ is not equivalent to a disjunction of pairwise distinct key types.
\end{itemize}
In the rest of this section we give a conservative extension of the translation defined so far that is total, i.e., it is defined for every TypeSpec type. The extension consists in defining approximations for the cases where the previous translation is undefined.

\subsection{Approximation of Bitstring Types}

Elixir Types has no plan to support bitstring types that is finer types than \texttt{binary()}, hence, it is not possible to directly translate any bitstring types 
However, most of the bitstring representatives could be trivially translated to \texttt{binary()}.
According to the Erlang documentation, bitstrings are a later generalization of binaries, so many texts and much information about binaries apply just as well for bitstrings.
%https://www.erlang.org/doc/system/expressions#bit-syntax-expressions
In other words, the purpose of bitstrings is to construct binaries in more precise manner.
Elixir Types provides type segments as Figure~\ref{app:bitstring-segment-types} that specify the $unit*size$ instead of direct notation with digits.
Interestingly, all the default segments are divisible by 8, that leads bitstring values to be accepted as binary types.

\begin{figure} [H]
   \[\begin{array}{rcll}
         Segment\,\,Type = \texttt{integer $|$ float $|$ binary $|$ bytes $|$ bitstring $|$ bits $|$ utf8 $|$ utf16 $|$ utf32}
   \end{array}\]
   \caption{Bitstring Segment Types}
   \label{app:bitstring-segment-types}
\end{figure}

Despite the rare use cases, bitstring types are still designed to be recognize $unit$ and $size$ other than digits divisible by 8 and these are not strictly accepted as \texttt{binary()}.
These types can be addressed as \texttt{binary() and dynamic()}.
Since bitstrings exist to generalize binaries as mentioned above, the specification should describe a binary type and otherwise realized at compile time.

\begin{figure} [H]
   \begin{translationfig}
      \dsb{\texttt{<<>>}} \approx \texttt{binary() and dynamic()}
      \nl 
      \dsb{\texttt{<<\_::$n$>>}} \approx 
      \left\{
         \begin{array}{ll}
            \texttt{binary()} & \textsl{if}\,\,\,\,n \bmod 8 = 0
            \nl
            \texttt{binary() and dynamic()} & \textsl{otherwise}
         \end{array}
      \right.
      \nl 
      \dsb{\texttt{<<\_::\_*$n$>>}} \approx 
      \left\{
         \begin{array}{ll}
            \texttt{binary()} & \textsl{if}\,\,\,\,n \bmod 8 = 0
            \nl
            \texttt{binary() and dynamic()} & \textsl{otherwise}
         \end{array}
      \right.
      \nl
      \dsb{\texttt{<<\_::$n$,\,\,\_::\_*$n$>>}} \approx 
      \left\{
         \begin{array}{ll}
            \texttt{binary()} & \textsl{if}\,\,\,\,n \bmod 8 = 0
            \nl
            \texttt{binary() and dynamic()} & \textsl{otherwise}
         \end{array}
      \right.
   \end{translationfig}
   \caption{Approximation of bitstring Types}
   \label{app:approximation-of-bitstring-types}
\end{figure}

\subsection{Approximation of Top Function Types}

The top function type is union of all the functions with every arity to the top type as defined in Figure~\ref{app:top-function-type}.
Since the top function type already takes over all the other function types, it becomes not worthy to have all the other function types that the return type is a subtype of the top type.
In the perspective of memory space, it is only costly to define and have all the function types because the maximum arity is 255.

\begin{figure} [H]
   \[\begin{array}{rcll}
         \texttt{\fun{\dots}{any()}} \equiv \texttt{\fun{$none$}{any()}\,\,$|$\,\,\dots\,\,$|$\,\,\fun{(none()$_1$, \dots, none()$_{255}$)}{any()}}
   \end{array}\]
   \caption{Top Function Type}
   \label{app:top-function-type}
\end{figure}

However, Elixir Types will not directly define \texttt{fun()} as Figure~\ref{app:top-function-type}, due to the triviality of defining the list of function with all the possible arity.
While Elixir Types restricts the top type to be only \texttt{fun()}, keeping the semantic approach to the top function, 
TypeSpec has allowed to specify the return type of the top type which have to be taken into account when translating it.
Nevertheless, this leniency in expressiveness means nothing in practice, given that the Dialyzer does not differentiate the return type but only perceive any form of the top types as \texttt{...->any()}.
These finally lead approximation of the any top function types into \texttt{fun() and dynamic()}.

\begin{figure} [H]
   \begin{translationfig}
      \dsb{\texttt{(\fun{\dots}{\TST})}} \approx
      \left\{
         \begin{array}{ll}
            \texttt{fun()} & \textsl{if}\,\,\,\,\dsb{\TST}\,\approx\,\texttt{term()}
            \nl
            \texttt{fun() and dynamic()} & \textsl{otherwise}
         \end{array}
      \right.
   \end{translationfig}
   \caption{Approximation of Top Function Type}
   \label{app:approximation-of-top-function-type}
\end{figure}

\subsection{Approximation of Field Types}

Approximating field types is more delicate than the others hence care must be taken.
That is TypeSpec allows all the types to be specified as key types of field types.
Whereas, Elixir Types' syntax has separate key types so that the type system does not deal with infinite set of types when it comes to field typing.
There comes four cases when the filed types are not key types:

\begin{itemize}
   \item Type variables.
   \item Subtypes of key types.
   \item Supertypes of key types.
   \item Neither subtypes nor supertypes of key types.
\end{itemize}

The first case is simple since they are eventually types belong to the syntax.
All it requires is to recursively evaluate it.

As most of the types are evaluated as subtypes of key types, 
it is sound to under-approximate them to their supertypes in key types.
For example, Figure~\ref{app:record-value-access-function} shows a simple identity function that takes a record. 

\begin{figure} [H]
   \[\begin{array}{l}
      \texttt{@spec record\_val(\%\{\{atom()\}\,\,=>\,\,integer()\})\,\,::\,\,integer()}
      \\
      \texttt{def record\_val(x) when is\_map\_key(x,\,\,\{:ok\}),\,\,do:\,\,Map.get(x,\,\,\{:ok\})}
   \end{array}\]
   \nl 
   \[\begin{array}{c}
      \dsb{\texttt{@spec id\_record(\%\{\{atom()\} => integer()\}) :: integer()}}
      \nl\rotatebox[origin=c]{90}{$\approx$}\nl
      \dsb{\texttt{@spec id\_record(\%\{tuple() => integer()\}) :: integer()}}
      \nl\rotatebox[origin=c]{90}{$\approx$}\nl
      \texttt{\$ \%\{tuple() => integer()\} -> integer()}
   \end{array}\]
   \caption{Record Value Access Function}
   \label{app:record-value-access-function}
\end{figure}

The key type is specified to accept tuple with a singe atom type,
but Dialyzer will pass when the example function is applied to records with any type of tuples as key types.
That is complemented by conservative approximations of Elixir Types in pattern/guard analysis:
it states that a type cannot express the exact domain of a function
and henceforth under-approximation is used with the guards/pattern that can filter out unintended types of values, which is called potentially accepted type.

\begin{figure} [H]
   \[\begin{array}{rcl}
      \dsb{\texttt{[]}} &\lessapprox& \texttt{list()}
      \nl 
      \dsb{\tuple{\ov{\TST}}} &\lessapprox& \texttt{tuple()}
      \nl 
      \dsb{\texttt{(\fun{$\ov{\TST}}{\TST}$)}} &\lessapprox& \texttt{fun()}
   \end{array}\]
   \caption{Subtypes of Keytypes}
   \label{app:subtypes-of-keytypes}
\end{figure}

\texttt{list()} in key types is semantically a set of all the list types and \texttt{nonempty\_maybe\_improper\_list()} in TypeSpec is a basic type to describe all kind of lists including the empty list and improper lists.
What hinders us from direct translation is that \texttt{list()} does not include improper lists hence to be a subtype of \texttt{nonempty\_maybe\_improper\_list()}.
Notwithstanding, this is not a interesting part for the improper lists not meant to be used as the name suggests.
The over-approximation of \texttt{nonempty\_maybe\_improper\_list()}, therefore, is sound to be \texttt{list()}.
% Furthermore, Elixir Types is not aware of improper lists types since it is not even a kind of type often used and recognized by users.
% Which ensures safeness of this over-approximation for the future works in Elixir Types.

\begin{figure} [H]
   \[\begin{array}{rcl}
      \dsb{\texttt{nonempty\_maybe\_improper\_list(\TST$_1$, \TST$_2$)}} &\gtrapprox& \texttt{list()}
   \end{array}\]
   \caption{Supertypes of Keytypes}
   \label{app:supertypes-of-keytypes}
\end{figure}

Even though the last cases in TypeSpec are not in the key types in Elixir Types, they can be semantically translated.
Firstly, since \texttt{|} is not a type but a type operator, it can simply be approximated per se.
Following Figure~\ref{app:semantical-comprehension-of-operator} displays different syntaxes with the same semantics.

\begin{figure} [H]
   \[\begin{array}{c}
      \dsb{\texttt{@spec fun(\%\{atom() | binary() => integer()\}) :: integer()}}
      \nl\rotatebox[origin=c]{90}{$\approx$}\nl
      \texttt{\$ \%\{atom() or binary() => integer()\} -> integer()}
      \nl\rotatebox[origin=c]{90}{$\approx$}\nl
      \texttt{\$ \%\{atom() => integer() or binary() => integer()\} -> integer()}
      \nl\rotatebox[origin=c]{90}{$\approx$}\nl
      \texttt{\$ \%\{atom() => integer()\} or \%\{binary() => integer()\} -> integer()}
   \end{array}\]
   \caption{Semantical Comprehension of Or Operator}
   \label{app:semantical-comprehension-of-operator}
\end{figure}


With a little autopsy on \texttt{any()} and \texttt{none()} as key types, comprehending it does not require a lot of effort; what they do in field types.
\texttt{any()} as a key type expands to unions of all the types mapping to a value type.
On the contrary, \texttt{none()} eradicates the field in the record type, for there is no field type without a key type. 
Imagine a type system only with a set of types, i.e., \texttt{\{any(), none(), integer(), float(), binary()\}}.
Then, the translation of \texttt{\%\{any()\,\,=>\,\,integer()\}} expands it to \texttt{\%\{(none() or integer() or float() or binary())\,\,=>\,\,integer()\}}
Whereas, \texttt{\%\{none()\,\,=>\,\,any()\}} is collapsed into \texttt{\%\{\}} which is an empty record type.
It all seems easy and sound, except one nuisance that risen by the need of listing all the types to translate \texttt{any()} in key types.
