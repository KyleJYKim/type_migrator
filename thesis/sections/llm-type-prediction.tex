\chapter{Setup and Implementation}
\label{ch:llm-settings}

We fine-tune two models of deliberately contrasting design on the corpus of typechecker-accepted annotations: a large decoder-only model adapted parameter-efficiently, and a much smaller encoder--decoder fine-tuned in full.
The aim is not to crown one architecture but to find an effective way to infer the new types.
Both see the same data, the same prompt, and the same split, so that what differs is the modelling approach and not the material it learns from.

\section{Models}
\label{sec:llm-models}

\paragraph{Qwen2.5-Coder-7B (decoder-only).}
Our first model is \texttt{Qwen2.5-Coder-7B}~\cite{qwen25coder} (the base variant, not instruct).
This choice reflects three considerations.
First, the Qwen2.5-Coder technical report~\cite{qwen25coder} reports that this model matches or exceeds DeepSeek-Coder-7B-Base~\cite{deepseekcoder} and StarCoder2-7B~\cite{starcoder2} across standard code benchmarks while remaining single-GPU deployable.
Second, its pretraining includes Elixir: the technical report~\cite{qwen25coder} lists Elixir among the 92 programming languages spanned by its more than 5.5~T tokens.
We treated documented Elixir coverage as a requirement, which ruled out otherwise-comparable models whose pretraining data is not documented to contain any.
Third, we use the base variant rather than the instruction-tuned one.
Because we fine-tune on a fixed prompt template of our own (Subsection~\ref{sec:llm-task}), the instruction-following an instruct variant adds is redundant, while its chat-format tuning would instil conversational habits---preambles, explanations, surrounding prose---that a task demanding only a bare type annotation would then have to suppress; a base checkpoint carries none to override.
Using base checkpoints for both models also keeps the comparison on equal footing, with neither carrying an extra layer of alignment tuning.

\paragraph{CodeT5+-770M (encoder--decoder).}
Our second model is \texttt{CodeT5+-770M}~\cite{codet5p}, an encoder--decoder an order of magnitude smaller than the Qwen2.5 base.
We chose it as a deliberately contrasting model: a different architecture, and much smaller.
As an encoder--decoder it encodes the full input before decoding, and it is pre-trained end-to-end for code understanding and generation~\cite{codet5p}.

\section{Fine-tuning and Hyperparameters}
\label{sec:llm-training}

The two models are adapted by different regimes. 
Since the aim is the best inference each model can give rather than a controlled comparison between them, we tune each independently for its own best performance; only the dataset, split, and prompt are held in common (Section~\ref{sec:llm-dataset}).

\paragraph{Qwen2.5: QLoRA.}
At 7~B parameters the model cannot be fully fine-tuned on a single GPU within reasonable time, and the supervised dataset is too small to benefit from full fine-tuning regardless.
We therefore apply QLoRA~\cite{qlora}: the base model is loaded in 4-bit NormalFloat (NF4) quantisation with double-quantisation enabled, and a Low-Rank Adaptation (LoRA)~\cite{lora} layer is attached to all seven linear sub-modules of every transformer block (\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj}, \texttt{gate\_proj}, \texttt{up\_proj}, \texttt{down\_proj}).
The LoRA rank is 32 with $\alpha = 64$ and a dropout of 0.05, giving roughly 80~M trainable parameters out of the 7~B base.
Training uses the HuggingFace \texttt{TRL} \texttt{SFTTrainer} with sequence packing at a maximum length of 1{,}024 tokens.
As a decoder-only model, it takes the prompt and the target annotation as one concatenated sequence and is trained by next-token prediction over the whole of it (the standard autoregressive objective).

\paragraph{CodeT5+: full fine-tuning.}
The 770~M encoder--decoder is small enough to fine-tune in full: all of its parameters are updated, with no adapters or quantisation.
Being a sequence-to-sequence model, it does not concatenate the two: the prompt is the encoder input, read bidirectionally, and the annotation is the decoder's target, so the training loss falls on the annotation tokens alone.
Its decoder output is capped at 512 tokens, which covers every target the length filter of Subsection~\ref{sec:llm-data-prep} keeps, and its encoder input at 1{,}536, which covers every prompt the types-in-scope cap allows (the longest is under 1{,}400 tokens), so no input is truncated.
Because attention cost grows with the square of the encoder length, this run uses a per-device batch of 2 with 8 gradient-accumulation steps and gradient checkpointing, holding the effective batch at 16.

\paragraph{Shared training configuration.}
Both runs use an effective batch size of 16 (Qwen2.5: per-device 2 with 8 gradient-accumulation steps; CodeT5+: likewise 2 with 8), a learning rate of $1 \times 10^{-4}$ with cosine decay and a 10\% warmup ratio, weight decay 0.01, and bfloat16 mixed precision.
The optimiser is paged AdamW with 8-bit state, and both train for 1.2 epochs, each retaining the checkpoint with the lowest validation loss (Section~\ref{sec:llm-repro}).

\section{Compute Environment}
\label{sec:llm-compute}
All training runs were carried out on the LIP6 Convergence cluster, where each job was allocated through Slurm a single NVIDIA~A100 GPU, 8 CPU cores, and host RAM.
Runs used a full A100 (the \texttt{a100\_7g.80gb} profile, 80~GB); because the 4-bit QLoRA configuration keeps the 7~B base model, its LoRA adapters, and optimiser state comfortably within 40~GB, a half-GPU MIG slice (the \texttt{a100\_3g.40gb} profile, 40~GB) was equally effective where it was used, and no run approached its time or memory limit.
The compatibility evaluation, which requires the compiler with the typechecker, was run separately on a local workstation.

With the models and their training regime fixed, we now turn to the pipeline that turns the checker-verified corpus into predictions: how the training dataset is prepared, and the code that fine-tunes the models and generates their annotations.

\section{Dataset Preparation}
\label{sec:llm-dataset}

This section turns the corpus of typechecker-accepted annotations into a supervised learning dataset: it settles the both-pass pool it draws from and its train/validation/test split, then frames the prediction task and the prompt the model is trained on.

\subsection{The Both-Pass Corpus and Split}
\label{sec:llm-data-prep}

We train on the \emph{both-pass} pool: every entry on which both Dialyzer and the set-theoretic typechecker accept the translated annotation, that is passed.
This is the largest checker-accepted pool, and it admits annotations whose translation contains \texttt{dynamic()}---overwhelmingly an artefact of unresolved remote types rather than a deliberate gradual-typing choice (Subsection~\ref{sec:approximation-via-dynamic}), but a type the checker nonetheless accepts as safe.
A length filter is applied before the split: entries whose function definition exceeds 2{,}000 characters or whose target annotation exceeds 1{,}000 characters are removed, as these pathological cases (e.g.\ \texttt{Regex.replace/4}, whose translation expands to over 250~KiB\footnote{Its third argument is typed \texttt{(... -> String.t())}, a variable-arity function whose non-\texttt{term()} return type the translation expands into a union over every fixed arity the BEAM permits, from 0 to 255 (Chapter~\ref{ch:formalisation}); a 616-character definition thereby yields an annotation of over 250~KiB.}) would dominate batch composition without proportionate learning signal.

\paragraph{Subproject-stratified split.}
The dataset is partitioned so that evaluation never sees a project it trained on: reusing functions from a training project would over-estimate generalisation.
The \texttt{project} field denotes a GitHub organisation, not a codebase (an organisation such as \texttt{mbta} hosts more than a hundred independent repositories), so we split by \emph{subproject}, defined as \texttt{project/module\_root} where \texttt{module\_root} is the top-level segment of the Elixir module path (e.g.\ \texttt{mbta/AlertProcessor}).

Each subproject is assigned to a split by hashing its name: we take the MD5 digest of the subproject name prefixed with the seed---the string \texttt{42:mbta/AlertProcessor}, for instance---read the digest as an integer, and reduce it modulo 100 to a bucket in $[0,100)$; buckets $[0,70)$ are \emph{train}, $[70,85)$ \emph{validation}, and $[85,100)$ \emph{test}. Every function of a subproject inherits that one bucket, so no subproject can leak across the three splits.

Hashing the \emph{name}, rather than shuffling the subproject universe, is what buys stability. A shuffle assigns splits by permuting the whole set, so regenerating the dataset---adding a repository, or dropping one that no longer compiles under the development compiler---reshuffles the assignment and can move a subproject from test into train; the test set then differs between rounds, silently invalidating any comparison of results across them. A per-name hash, by contrast, is a pure function of the subproject and the fixed seed, independent of every other subproject, so an assignment never changes as the corpus grows---and that fixed test set is what makes results comparable across training rounds.

The resulting proportions are approximate, and deliberately so.
The ratio is exactly 70/15/15 over the hash range, but a finite set of subprojects cannot realise it exactly: by \emph{count} the split lands at 279/60/64 (69/15/16\%), the ordinary sampling spread of dropping 403 independent items into fixed buckets.
By \emph{entries} it drifts further, to 63.8/22.5/13.7\% (Table~\ref{tab:llm-splits})---validation above and training below the nominal share---because the split unit is the whole subproject while entries are counted per function, and subprojects vary widely in size, so a few large ones landing in validation tilt the totals; this imbalance is one no choice of hash can remove, since it stems from the coarse split unit rather than from the hash.
We treat precise proportions as subordinate to a test set that is leak-free and stable across rounds, and the two changes that would tighten the ratio each forfeit exactly one of those guarantees: splitting by \emph{entry} would balance the counts but leak sibling functions of one subproject across splits, while counting up to an exact 70\% would nail the ratio but tie every assignment to the whole corpus, so that adding or dropping a single repository would reshuffle the test set.
A split that never leaks and never shifts between rounds is worth more here than an exact one that does either.

\subsection{Task Formulation}
\label{sec:llm-task}

We frame type prediction as a \emph{conditional text-generation} task: given the definition of a function (i.e., its source text together with any user-defined types in its module scope) the model writes out the corresponding Elixir Type annotation one token at a time, much as a language model produces a sentence.
It is \emph{conditional} because what the model writes depends on the input code, and \emph{generation} because the annotation is produced as text rather than selected from a fixed set of labels, which is necessary here because the new Elixir type system is open-ended (arbitrary unions, tuples, and maps with explicit fields) and forms no finite vocabulary to classify into.

Each training entry consists of:
\begin{itemize}
    \item the qualified module name in which the function is defined;
    \item the \texttt{@type}, \texttt{@opaque}, and \texttt{@typep} declarations in scope at the function, themselves translated into Elixir Types, so that the context the model reads is in the notation it must write;\footnote{The declarations are recorded in the dataset in their original TypeSpec form and translated by the same equations as the target (Chapter~\ref{ch:formalisation}). The block is capped at 2{,}000 characters, whole declarations only: translation \emph{expands} a type, and a declaration containing a variable-arity \texttt{(... -> T)} reaches over 500~KiB once the union over arities is written out (Subsection~\ref{sec:llm-data-prep}). The cap binds on \num{4.3}\% of entries and retains \num{97.8}\% of all declarations.}
    \item the function definition reconstructed from the AST, including all clauses when there are more than one;
    % \item two \emph{grounding} blocks extracted from that definition, which surface the evidence the code itself provides for the type: the \emph{argument patterns} (each clause's parameter patterns and guards, e.g.\ \texttt{(\%User\{\}, \_) when is\_binary(x)}) and the \emph{return expressions} (the outermost constructor of each clause's tail position, e.g.\ \texttt{\{:ok, \_\}} or, for a value produced by an opaque call, \texttt{call: fetch/1});
    \item the target: the translated annotation, already accepted by the typechecker.
\end{itemize}

These fields are assembled at runtime into a structured prompt with delimiter sections. It is built once and shared verbatim by both models---everything up to and including the \texttt{\#\#\# Output:} marker:
\begin{lstlisting}[numbers=none]
"### Instruction":
    "For the given Elixir function definition, infer the most precise correct
     function type, written as an Elixir set-theoretic type annotation.
     Respond only with Elixir Types (Descr) syntax."

"### Input":
    "Module": MODULE_NAME
    "Definition": FUNCTION_DEFINITION
    "Types in scope": USER_DEFINED_TYPES

"### Output":
\end{lstlisting}
The definition precedes the types in scope deliberately: should a prompt ever exceed a model's input window, truncation removes the tail, and the expendable part must be there.
With the types first, an oversized declaration could consume the window and cut away the definition and the \texttt{\#\#\# Output:} marker themselves, leaving the model to answer from a fragment of a type.

The target annotation is what follows that marker:
\begin{lstlisting}[numbers=none]
    FUNCTION_ANNOTATION
\end{lstlisting}
The \texttt{\#\#\# Output:} marker is the seam at which the two architectures diverge---the one point where they treat the same text differently.
For the decoder-only model (Qwen2.5), prompt and target form a single continuous token stream: the prompt up to \texttt{\#\#\# Output:} is fed in and the model \emph{continues} it, emitting the annotation, and a terminating end-of-text token, as the completion of that same sequence.
For the encoder--decoder (CodeT5+), the two are separate streams: the identical prompt is the \emph{encoder} input, read in full and bidirectionally, while the annotation is generated on the \emph{decoder} side as its own target sequence.
The supervised objective is the same either way---given the definition, produce, token by token, the annotation the typechecker accepts---but the decoder-only model is trained over the whole concatenated sequence, whereas the encoder--decoder places its loss on the target tokens alone (Section~\ref{sec:llm-training}).

The template uses the familiar Alpaca-style \texttt{\#\#\# Instruction}/\texttt{\#\#\# Input}/\texttt{\#\#\# Output} headers, yet both models are base, pre-trained checkpoints, not instruction-tuned variants (Section~\ref{sec:llm-models}).
The headers are therefore not there to trigger instruction-following---a base model has learned none---but act as fixed structural delimiters imposed identically during fine-tuning and at inference (the same template is the single source of truth for both).
The model thus learns the format from the supervised data: the annotation is what follows the \texttt{\#\#\# Output:} marker.
The natural-language instruction line is itself a constant prefix, identical across every example, so a base model need not interpret it as a command for the mapping to be learned.
An instruction-tuned model, by contrast, would read such a header through its own learned instruction-following and would normally be driven through its dedicated chat template and special role tokens; we instead supply a plain, fixed scaffold and teach its role through fine-tuning.

\section{Training Pipeline}
\label{sec:llm-pipeline}
The pipeline is a handful of Python scripts sharing one prompt module.
\texttt{prepare\_data.py} consumes the translation prototype's dataset (Chapter~\ref{ch:implementation}), keeps the both-pass entries, applies the length filter, and writes the seed-scoped \texttt{train}/\texttt{validation}/\texttt{test} splits of Subsection~\ref{sec:llm-data-prep}.
The prompt template of Subsection~\ref{sec:llm-task} lives in a single module imported by both trainers and both generators, so the format cannot drift between training and inference---a silent prompt mismatch there would degrade generation without raising any error.

Two scripts realise the regimes of Section~\ref{sec:llm-training}.
The decoder-only script wraps the base model in QLoRA and trains with the \texttt{TRL} \texttt{SFTTrainer}, packing prompt and target into one sequence and taking the loss over all of it.
The encoder--decoder script fully fine-tunes CodeT5+ with a \texttt{Seq2SeqTrainer}; its \texttt{DataCollatorForSeq2Seq} right-shifts the decoder input and sets the label of every padding position to $-100$, so the cross-entropy falls on the annotation tokens alone.
Both evaluate on the validation split as training proceeds and retain the checkpoint of lowest validation loss (Section~\ref{sec:llm-repro}).

\section{Training Behaviour and Reproducibility}
\label{sec:llm-repro}
Both runs converge without instability.
Qwen2.5 trains for \num{220} optimiser steps in \num{10996}~seconds (about three hours); its training loss falls smoothly from \num{1.21} to a run-mean of \num{0.54}, with small and stable gradient norms throughout.
CodeT5+ trains for roughly \num{741} steps in \num{3803}~seconds (about \num{63} minutes), its training loss dropping from \num{2.43} to a run-mean of \num{0.27} after a noisier early phase.

The two validation curves differ in a way that bears on checkpoint selection (Figure~\ref{fig:llm-loss-curves}).
Qwen2.5's validation loss bottoms early---\num{0.694} at about epoch~\num{0.44}---and drifts upward to \num{0.713} thereafter, so the retained checkpoint is an intermediate one rather than the final weights.
CodeT5+'s bottoms late---\num{0.276} at about epoch~\num{0.97}---and stays essentially flat to the end, so its best and final checkpoints nearly coincide.
In both cases the model carried forward to evaluation is the one that minimises validation loss.

\paragraph{The proxy and the metric can disagree.}
One observation from these runs bears directly on that selection rule.
Both models were also trained in an earlier round whose prompt supplied the types in scope in their original TypeSpec form rather than translated (Subsection~\ref{sec:llm-task}); everything else was held fixed.
Between the two rounds Qwen2.5's best validation loss fell from \num{0.885} to \num{0.694}, a \num{22}\% improvement, while its compatibility on the test set fell slightly, from \num{36.6}\% to \num{35.9}\%.
CodeT5+ moved the other way: its best validation loss was unchanged at \num{0.276}, while its compatibility rose from \num{54.3}\% to \num{56.3}\%.
Cross-entropy on held-out targets and compatibility with a reference are therefore not merely different scales but can move in opposite directions, which is the concrete form of the caveat attached to selecting checkpoints by validation loss (Section~\ref{sec:future-work}).

\paragraph{Provenance of the two runs.}
Each run records the prompt format it used---the instruction text, which fields the blocks were built from, the character budget, and a hash of the prompt module's source---alongside a sample of the exact training texts and every generation prompt with its raw output.
The four phases of the comparison (both models, training and generation) record the same prompt-module hash, so the two models demonstrably read prompts built by the same code rather than by two copies of it that had drifted apart.
The same logs confirm that no prompt was truncated on the encoder side and none was skipped for length, and that \num{13} training and \num{8} validation examples were dropped for exceeding Qwen2.5's \num{1024}-token packing window.

\section{Generation}
\label{sec:llm-generation}
A trained model is run over the held-out test split by \texttt{generate.py} (Qwen2.5) or \texttt{generate\_seq2seq.py} (CodeT5+): each entry's prompt is fed to the model, which decodes greedily to produce one annotation.

Qwen2.5's decoding is \emph{grammar-constrained}.
A GBNF grammar encodes the entire set-theoretic type syntax---unions, intersections, negation, the base types, \texttt{dynamic()}, function types, lists, tuples, and maps with \texttt{if\_set} fields---and a grammar-constrained logits processor masks, at every decoding step, every token that would break the grammar.
The model can therefore emit only well-formed Descr types: balanced delimiters, terminated atoms, and no drift into TypeSpec forms such as \texttt{String.t()} or \texttt{any()}.
A light repetition penalty and a per-entry time budget additionally break the degenerate enumeration loops into which a constrained greedy decoder can otherwise fall.
CodeT5+ is decoded \emph{unconstrained}: the same grammar cannot be applied because the constrained-decoding library does not support its tokenizer, which is the source of its higher null rate (Section~\ref{sec:llm-results}).

Each run writes one record per test entry---the generated annotation alongside its reference---to a predictions file.\footnote{A reference longer than the generation budget cannot be emitted in full; such entries are flagged, so the metric is not charged for a truncation the budget, not the model, caused.}
Because every prediction is itself a concrete Descr type, it could be injected back into its source project and recompiled as an end-to-end check; the evaluation in this thesis instead scores each prediction directly against its reference with the type system's own compatibility judgement (Chapter~\ref{ch:llm-eval}).

\chapter{Evaluation}
\label{ch:llm-eval}

A trained model is evaluated by comparing each predicted annotation against the accepted reference annotation on the held-out test entries.
Because the target is a set-theoretic type, we evaluate a prediction not by textual similarity to the reference but by whether it is a type the reference does not contradict, using the type system's own compatibility judgement.

\section{Set-Theoretic Compatibility}
\label{sec:compatibility-eval}

The question a metric must answer is not whether the prediction is textually identical to the reference, but whether it is a \emph{safe} type for the function: one the reference does not contradict.
This is exactly the judgement the set-theoretic type system already provides, hence, we score predictions with the type algebra the typechecker itself is built on: the compiler's internal \texttt{Module.Types.Descr} module, which represents types as sets of values and defines union, intersection, negation, and subtyping as set inclusion (Chapter~\ref{ch:formalisation}).

\paragraph{Why not exact match.}
The most direct metric is exact-match accuracy: the fraction of test entries on which the prediction is the reference.
Taken literally, as equality of the two annotation strings, it is uninformatively strict for set-theoretic types.
Two annotations that describe the identical set of values, for instance a union written as \texttt{A or B} versus \texttt{B or A}, or a map written with one field ordering versus another, are semantically equal but textually distinct; conversely two annotations may differ in a single atom yet denote entirely different value sets.
We therefore decide exact match set-theoretically instead, with the same module's \texttt{subtype?/2}: a prediction matches exactly when it is a subtype of the reference \emph{and} the reference a subtype of it, mutual inclusion being the set-theoretic statement that the two denote the identical set of values.
A difference of union-arm or map-field ordering, or a redundant arm, therefore does not count against a prediction, whereas a single atom that changes the denoted set does.
Even so decided, exact match is the wrong primary criterion.
It is strictly stronger than compatibility (below), additionally requiring equal \emph{precision} rather than mere safety, so it penalises a prediction that is a \emph{sound} answer merely for being less precise than the reference, which is the wrong signal for a migration setting where a safe over-approximation is a success, not a failure.
We therefore report it alongside compatibility only as an indicator of precision.

\paragraph{Compatibility.}
We therefore adopt \emph{compatibility}, computed by the \texttt{Descr.compatible?/2} relation: the gradual-typing consistency judgement of the set-theoretic system itself.
A predicted type is compatible with the reference when, treating \texttt{dynamic()} as a wildcard that may stand for any type, the two can be reconciled: the static (non-gradual) content of the prediction must lie within the type the reference permits, so the prediction never \emph{asserts} a shape the reference forbids.
A compatible prediction is thus a safe annotation for the function.
It may be exactly the reference or strictly more general, the limiting case being \texttt{dynamic()} itself, which is compatible with every reference; both count as compatible, whereas a prediction that commits to a concrete shape the reference excludes does not.
This is the appropriate success criterion for a migration setting: an annotation is acceptable precisely when it does not conflict with the function's true type, even at some cost in precision.
Formally, where $\DTR$ represents a Descr component, $\ETR$ an Elixir type, $\ETD$ \texttt{dynamic()}, and where $L$ is the prediction and $R$ the reference ($L$ and $R$ are head letters of left and right, respectively, following the naming in the function definition):

\begin{figure} [H]
    \[
    \begin{prooftree}
        % \hypo{\ETR \;\rightsquigarrow\; \DSR_{grd}\ \ (\text{the \texttt{:dynamic} component}),\ \ \DSR_{stt}\ \ (\text{the static remainder})}
        \hypo{\DSR = \ETR \setminus \ETD}
        \infer1[Descr Component]{\DTR = (\DSR_{grd} \cap \ETD) \cup \DSR_{stt}}
        \infer1[Arguments of \texttt{compatible?/2}]{\DTR^{L} = (\DSR^{L}_{grd} \cap \ETD) \cup \DSR^{L}_{stt} & \DTR^{R} = (\DSR^{R}_{grd} \cap \ETD) \cup \DSR^{R}_{stt}}
    \end{prooftree}
    \]
    \nl \nl
    % \texttt{compatible?($\DTR^{L}$, $\DTR^{R}$)} = 
    % \texttt{compatible?($(\DSR^{L}_{grd} \cap \ETD) \cup \DSR^{L}_{stt}$, $(\DSR^{R}_{grd} \cap \ETD) \cup \DSR^{R}_{stt}$)}
    % \nl    
    \begin{translationfig}
    \texttt{compatible?($\DTR^{L}$, $\DTR^{R}$)} =  
    \left\{
        \begin{array}{ll}
            \texttt{true}
            & \textsl{if}\,\,\,\,((\DSR^{L}_{stt} = \emptyset)\,\,\textsl{and}\,\,(\DSR^{L}_{grd} \cap \DSR^{R}_{grd} \neq \emptyset))
            \nl
            & \textsl{or}\,\,((\DSR^{L}_{stt} \neq \emptyset)\,\,\textsl{and}\,\,(\DSR^{L}_{stt} \leq \DSR^{R}_{grd}))
            \nl
            \texttt{false} & \textsl{otherwise}

            % \texttt{true}
            % & \textsl{if}\,\,\,\,((\DSR^{L}_{stt} = \emptyset)\,\,\textsl{and}\,\,(\DSR^{L}_{grd} \cap \DSR^{R}_{grd} \neq \emptyset))
            % \nl
            % & \textsl{or}\,\,(\DSR^{L}_{stt} \leq \DSR^{R}_{grd})
            % \nl
            % \texttt{false} & \textsl{otherwise}
        \end{array}
    \right.
    \end{translationfig}
   \caption{Descr Compatibility}
   \label{app:descr_compatibility}
\end{figure}

A Descr component is the union of a gradual part and a static part: the gradual part is a type representation intersected with \texttt{dynamic()}, and the static part is another type representation.
If the static part is empty, the type is fully gradual (e.g.\ \texttt{dynamic(integer())}); if both parts are present, the type has at least one \texttt{dynamic()} in its union (e.g.\ \texttt{dynamic(integer()) or atom()}), and the gradual part then also contains the static part, since it records the largest type the value may have at runtime; and if there is no gradual part at all, the type is fully static (e.g.\ \texttt{integer()}), in which case \texttt{compatible?/2} uses the type itself in place of the gradual part.
The function takes two Descr components, $\DTR^L$ and $\DTR^R$: in our case, the prediction and the reference.
It splits $\DTR^L$ into the type representations of both its parts, $\DSR^L_{grd}$ and $\DSR^L_{stt}$, and takes from $\DTR^R$ only its gradual part $\DSR^R_{grd}$ (or $\DTR^R$ itself, if it is fully static).
It then branches on whether $\DSR^L_{stt}$ is empty: if it is, compatibility holds exactly when $\DSR^L_{grd}$ and $\DSR^R_{grd}$ overlap, that is, when their intersection is non-empty; if it is not, compatibility holds exactly when $\DSR^L_{stt}$ is a subtype of $\DSR^R_{grd}$.
This is lenient where the prediction is fully gradual, which need only overlap the reference, while a prediction with static content must fit within the largest type the reference admits.

\paragraph{Computation.}
Each prediction and reference is parsed into a \texttt{Descr} value by our own parser, which reads the annotation string as Elixir syntax and rebuilds it with \texttt{Descr}'s constructors (the typechecker itself never reads such strings); parsing collapses whitespace and union-arm ordering and rewrites any \texttt{|} to \texttt{or} (the model occasionally emits the TypeSpec union symbol out of pretraining habit, though the target system writes unions only as \texttt{or}).
The two values are then submitted to \texttt{compatible?/2}, the same relation the typechecker applies when it checks an expression against an expected type.
A prediction that fails to parse is counted as not compatible (reported separately as \emph{null}).

\section{Results}
\label{sec:llm-results}

Both models are scored on the common \num{2127}-entry test set, having trained on the same both-pass dataset with the same prompt, so any difference is attributable to the model rather than the data.
One asymmetry must be stated: the Qwen2.5 decoding is grammar-constrained to well-formed set-theoretic types, whereas the CodeT5+ decoding is \emph{unconstrained}, because the constrained-decoding library does not support its tokenizer; we therefore report each model's null rate.

The smaller encoder--decoder is the stronger model on both axes.
It is more compatible (\num{56.3}\% versus \num{35.9}\%, \num{1198} entries against \num{763}, a \num{20.5}-point margin) and far more precise, matching the reference exactly on \num{29.5}\% of entries against \num{7.7}\% for Qwen2.5 (\num{627} against \num{164}, nearly four times as many), while decoding without the grammar constraint and at roughly a tenth of the parameters.
The one cost of the missing constraint is CodeT5+'s higher null rate (\num{4.4}\% against \num{2.0}\%): these malformed outputs are counted against it as incompatible.
That handicap---\num{2.4} points more null than Qwen2.5, all charged against CodeT5+---is far smaller than its \num{20.5}-point compatibility margin, so the unconstrained decoding does not account for the gap.
Full fine-tuning of a task-matched encoder--decoder thus outperforms parameter-efficient adaptation of a much larger decoder-only model on this task.

\paragraph{How the compatibility is earned.}
Because the evaluator records both directions of \texttt{subtype?/2}, each prediction falls into one of four cases against its reference, and the two models earn their compatibility differently (Table~\ref{tab:llm-distance}).
Predictions that are equal to the reference or narrower than it are compatible by construction, and every one of them is: \num{164} and \num{172} for Qwen2.5, \num{627} and \num{197} for CodeT5+.
The remaining compatible predictions are ones the reference neither contains nor is contained by, admitted because the reference is gradual and a \texttt{dynamic()} position accepts anything.
For Qwen2.5 those account for \num{390} of its \num{763} compatible predictions (\num{51}\%); for CodeT5+, \num{324} of \num{1198} (\num{27}\%).
Qwen2.5's compatibility therefore rests about twice as heavily on references too weak to contradict it, so the \num{20.5}-point margin understates the distance between the two models on the entries where the reference has something to say.

\section{Qualitative Analysis}
\label{sec:llm-qualitative}
\label{sec:qualitative}

Inspecting individual predictions makes the behaviour behind the aggregate numbers concrete. All examples below are drawn verbatim from the models' outputs on the common test set.

\paragraph{Exact matches a string comparison would miss.}
Some predictions differ textually from the reference yet denote the identical type, which mutual subtyping credits as an exact match where a naive string comparison would not.
\texttt{Membrane.RTP.Packet.PayloadType.dynamic?/1} has reference \texttt{(integer() or integer() -> :true or :false)}; both models predict \texttt{(integer() -> :true or :false)}, collapsing the redundant union \texttt{integer() or integer()} to the identical \texttt{integer()}.
Each type is a subtype of the other, so the prediction counts as exact for both models.

\paragraph{Where the larger model fails and the smaller succeeds.}
The architecture comparison of Section~\ref{sec:llm-results} shows up in individual predictions, and one failure shape recurs: Qwen2.5 answers with a \emph{struct} where the reference is a plain primitive.
\texttt{CSSHelpers.string\_to\_class/1} has reference \texttt{(binary() -> binary())}; Qwen2.5 predicts \texttt{(binary() -> dynamic(\%\{atom() => if\_set(term()), :\_\_struct\_\_ => :"Elixir.String"\}))}, an open struct named \texttt{String}, whereas CodeT5+ reproduces the reference exactly.
\texttt{CMS.Helpers.rewrite\_url/1} has the same reference and draws the same shape from Qwen2.5, this time named \texttt{URI}.
\texttt{Membrane.Matroska.Schema.element\_id\_to\_name/1} has reference \texttt{(integer() -> atom())}, where Qwen2.5 predicts \texttt{(integer() -> binary())}---the right arity and argument, the wrong leaf type---and CodeT5+ is again exact.
The pattern is measurable rather than anecdotal: among Qwen2.5's \num{1364} non-compatible predictions, \num{253} name a struct the reference does not contain, against \num{33} of CodeT5+'s \num{929}.
In \num{21} of Qwen2.5's cases the invented struct is \texttt{String}, which is not a struct in Elixir at all---a shape no reference in the corpus could have taught it.

We are deliberately cautious about the cause: CodeT5+ and Qwen2.5 differ in more than their encoder --- also in fine-tuning regime (full versus low-rank adaptation), pretraining corpus and objective, and parameter count --- so this single comparison cannot attribute the gap to any one factor.
One plausible contributor is architectural: an encoder--decoder reads the whole function definition bidirectionally before the decoder fixes any output position, a fuller view of the code's evidence than a strictly left-to-right, decoder-only pass affords.

The two models also inherit different task formulations.
An encoder--decoder is the classical formulation for sequence-to-sequence transduction: the Transformer was introduced in exactly that shape, one stack reading the input and another producing the output, for machine translation~\cite{vaswani2017}, and CodeT5+ is pre-trained end-to-end in that mould for code understanding and generation~\cite{codet5p}.
The decoder-only alternative instead recasts such a task as the continuation of a single concatenated sequence, the more recent convention popularised by large autoregressive language models~\cite{gpt3}; it is the more general formulation, but the less specialised one for a fixed input-to-output transduction of the kind considered here.
Controlled comparisons outside our setting point the same way.
Raffel et al.~\cite{t5}, comparing architectures at matched parameter and compute budgets, report that the encoder--decoder performed best on every task they tried, and that it outperforms a decoder-only prefix language model that sees its input bidirectionally but shares one stack for input and output.
Wang et al.~\cite{wang2022architecture} find that a causal decoder-only model generalises best zero-shot after self-supervised pretraining alone, but that models with non-causal visibility over their input do best once they are finetuned---the regime ours are in.
Neither study concerns type prediction, and both vary the pretraining objective alongside the architecture, so they corroborate the mechanism rather than establish it here.
Isolating the encoder's contribution --- for instance by fully fine-tuning a decoder-only model of comparable scale under an otherwise identical regime --- is left to future work.

\section{Summary}
\label{sec:llm-summary}

\begin{itemize}
    \item \textbf{Corpus and split}: the \num{18688} annotations accepted by both checkers (Chapter~\ref{ch:implementation}) are length-filtered and partitioned by hashing the name of each subproject, so that no subproject can appear in more than one split, yielding \num{9888} training, \num{3484} validation, and \num{2127} test entries over 279/60/64 subprojects (Subsection~\ref{sec:llm-data-prep}).
    \item \textbf{Task}: prediction is framed as conditional generation---given a function definition and the types in scope, write the annotation as text---under one prompt template shared verbatim by both models, which diverge only in how they consume it: a single concatenated stream for the decoder-only model, separate encoder and decoder streams for the encoder--decoder (Subsection~\ref{sec:llm-task}).
    \item \textbf{Training}: \texttt{Qwen2.5-Coder-7B} was adapted with QLoRA and \texttt{CodeT5+-770M} fully fine-tuned, both for 1.2 epochs on identical data. Both runs converged without instability, and each model carried forward is the checkpoint of lowest validation loss: \num{0.694} at epoch~\num{0.44} for Qwen2.5, whose curve drifts upward thereafter, and \num{0.276} at epoch~\num{0.97} for CodeT5+, whose curve stays flat to the end. Both runs record the same prompt-module hash, so the two models read prompts built by one and the same code (Section~\ref{sec:llm-repro}).
    \item \textbf{Metric}: predictions are judged by Elixir's own \texttt{compatible?/2} in \texttt{Module.Types.Descr}, which accepts a prediction exactly when the reference does not contradict it, with exact match---decided by the same module's \texttt{subtype?/2} in both directions---reported alongside as an indicator of precision and unparseable output counted as incompatible (Section~\ref{sec:compatibility-eval}).
    \item \textbf{Results}: on the common \num{2127}-entry test set CodeT5+ is compatible on \num{56.3}\% of entries against \num{35.9}\% for Qwen2.5, a \num{20.5}-point margin, and exact on \num{29.5}\% against \num{7.7}\%---the smaller model ahead on both axes at roughly a tenth of the parameters and without the grammar constraint Qwen2.5 decodes under. The cost of that unconstrained decoding, a null rate \num{2.4} points higher and charged against CodeT5+ as incompatible, is far smaller than its margin. Of the compatible predictions, \num{51}\% of Qwen2.5's are admitted only because the reference is gradual, against \num{27}\% of CodeT5+'s, so the margin understates the gap where the reference constrains the answer (Section~\ref{sec:llm-results}).
    \item \textbf{Qualitative behaviour}: deciding equality by mutual subtyping credits predictions that differ textually from the reference yet denote the same type, which a string comparison would miss; in the failures examined, Qwen2.5 answers with a struct where the reference is a plain primitive---\num{253} of its \num{1364} failures name a struct the reference does not contain, against \num{33} of CodeT5+'s \num{929} (Section~\ref{sec:llm-qualitative}).
    \item \textbf{Attribution}: the two models differ in architecture, scale, and fine-tuning regime at once, so the gap is not attributed to any single factor. The encoder's bidirectional read of the definition is a plausible contributor, and controlled architecture comparisons outside this setting point the same way~\cite{t5,wang2022architecture}, but isolating it would require a further experiment.
\end{itemize}
Within the envelope the length filter keeps, a fine-tuned model can therefore propose an annotation the reference accepts for slightly more than half of the held-out functions, and reproduce the reference exactly for close to three in ten.
These figures measure agreement with a reference annotation; what they do not measure is whether such a prediction carries its function through migration in its own project, which would require compiling it back into the source.
