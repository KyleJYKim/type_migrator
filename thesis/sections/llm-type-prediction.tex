\section{LLM Type Prediction}

Having established a corpus of typechecker-accepted annotations, we now ask whether a language model can \emph{produce} such annotations from a function's source alone.
Because the target is a set-theoretic type, we evaluate a prediction not by textual similarity to the reference but by whether it is a type the reference does not contradict, using the type system's own compatibility judgement (Subsection~\ref{sec:compatibility-eval}).

\subsection{Task Formulation}
\label{sec:llm-task}

We frame type prediction as a \emph{conditional text-generation} task: given the definition of a function (i.e., its source text together with any user-defined types in its module scope) the model writes out the corresponding Elixir Type annotation one token at a time, much as a language model produces a sentence.
It is \emph{conditional} because what the model writes depends on the input code, and \emph{generation} because the annotation is produced as text rather than selected from a fixed set of labels, which is necessary here because the new Elixir type system is open-ended (arbitrary unions, tuples, and maps with explicit fields) and forms no finite vocabulary to classify into.

Each training entry consists of:
\begin{itemize}
    \item the qualified module name in which the function is defined;
    \item the list of \texttt{@type}, \texttt{@opaque}, and \texttt{@typep} declarations in scope at the function;
    \item the function definition reconstructed from the AST, including all clauses;
    \item two \emph{grounding} blocks extracted from that definition, which surface the evidence the code itself provides for the type: the \emph{argument patterns} (each clause's parameter patterns and guards, e.g.\ \texttt{(\%User\{\}, \_) when is\_binary(x)}) and the \emph{return expressions} (the outermost constructor of each clause's tail position, e.g.\ \texttt{\{:ok, \_\}} or, for a value produced by an opaque call, \texttt{call: fetch/1});
    \item the target: the translated annotation, already accepted by the typechecker.
\end{itemize}

These fields are assembled into a structured prompt with delimiter sections (\texttt{\#\#\# Module:}, \texttt{\#\#\# Types in scope:}, \texttt{\#\#\# Definition:}, \texttt{\#\#\# Argument patterns:}, \texttt{\#\#\# Return expressions:}, \texttt{\#\#\# Elixir type:}), with the target annotation placed last.
The two grounding blocks make explicit, at the input, exactly the code evidence that the honest-labelling transforms of Subsection~\ref{sec:honest-labelling} rely on at the target: a type is expected only where a pattern, guard, or tail constructor supports it.
Training is plain next-token prediction over this whole text (the standard \emph{autoregressive} objective): at each position the model predicts the next token from all the tokens before it, so that, given the prompt up to \texttt{\#\#\# Elixir type:}, it learns to continue with the correct annotation.

This formulation differs from prior work in three respects.
First, the target type system is set-theoretic rather than nominal: predictions must produce unions, intersections, and constructor-shaped types with explicit field information, not class names.
Second, the task is type \emph{generation} rather than the type \emph{correction} studied by~\cite{Nina}.
There is no observed (potentially incorrect) type in the input, only the function definition; the model must produce the annotation from scratch.
Third, the language is Elixir on the BEAM, an under-represented target in code-LLM training corpora compared with Python or TypeScript, on which most existing type-prediction work has been conducted.

\subsection{Dataset Preparation and the Two-Track Design}
\label{sec:llm-data-prep}
\label{sec:two-track}

The evaluation in Section~\ref{sec:evaluation} established two candidate training pools, each justified by a different goal.
The first, which we call the \emph{both-pass} pool, keeps every entry on which both Dialyzer and the typechecker pass; it is the largest checker-accepted pool but admits annotations whose translation contains \texttt{dynamic()}.
The second, the \emph{no-gradual} pool, additionally removes any entry whose target annotation contains \texttt{dynamic()}, retaining only precise labels.
Because \texttt{dynamic()} is overwhelmingly an artefact of unresolved remote types rather than a deliberate gradual-typing choice (Subsection~\ref{sec:approximation-via-dynamic}), these two pools embody two opposing hypotheses about what a model \emph{should} be taught to produce.
Rather than choose between them a priori, we train one model on each and compare them directly, in a \emph{two-track} study:

\begin{itemize}
    \item \textbf{Track~1 (no-gradual)}: both tools pass, no \texttt{dynamic()} in the target. \num{4113} entries.
    \item \textbf{Track~2 (both-pass)}: both tools pass, \texttt{dynamic()} permitted. \num{7649} entries (= Track~1 plus \num{3536} gradual-containing entries).
\end{itemize}
A length filter is applied to both pools before the split: entries whose function definition exceeds 2{,}000 characters or whose target annotation exceeds 1{,}000 characters are removed, as these pathological cases (e.g.\ \texttt{Regex.replace/4}, whose translation expands to over 250~KiB\footnote{Its third argument is typed \texttt{(... -> String.t())}, a variable-arity function whose non-\texttt{term()} return type the translation expands into a union over every fixed arity the BEAM permits, from 0 to 255 (Chapter~\ref{ch:formalisation}); a 616-character definition thereby yields an annotation of over 250~KiB.}) would dominate batch composition without proportionate learning signal.
This filter removes \num{1455} entries from the \num{9104}-entry both-pass pool, leaving \num{7649}, but only 31 from its \num{4144}-entry dynamic-free subset, leaving \num{4113}.
Because the \texttt{dynamic()}-laden translations are precisely the ones that balloon in size, almost all of that cut (\num{1424} of \num{1455}) falls on gradual entries, so the gradual-containing residue is \num{3536} rather than the \num{4960} the unfiltered \num{9104} and \num{4144} pools would imply.

\paragraph{Subproject-stratified, aligned split.}
Both tracks are partitioned by a project-stratified split: evaluating on functions from a project that also appears in training would over-estimate generalisation.
The \texttt{project} field denotes a GitHub organisation, not a codebase (an organisation such as \texttt{mbta} hosts more than a hundred independent repositories), so we split by \emph{subproject}, defined as \texttt{project/module\_root} where \texttt{module\_root} is the top-level segment of the Elixir module path (e.g.\ \texttt{mbta/AlertProcessor}).
To keep the two tracks directly comparable, a \emph{single} subproject split is computed once over Track~2's subproject universe (the superset, since Track~1~$\subseteq$~Track~2) and applied to both tracks at a 70/15/15 target ratio.
The split assignment is a deterministic hash of each subproject name (a salted MD5 reduced modulo 100), rather than a shuffle of the universe, so that a subproject keeps its assignment across dataset regenerations: the test set is stable even as the corpus grows, which is what makes results comparable across training rounds.
This guarantees that the two tracks see the same subprojects in the same split and that no subproject leaks across train, validation, and test in either track.
The universe contains 247 subprojects (177 train / 28 validation / 42 test), yielding the entry counts in Table~\ref{tab:llm-splits}.

\paragraph{The common test set.}
Because both tracks share the split, Track~2's test set (912 entries) is a \emph{superset} of Track~1's (400 entries), the latter being exactly its dynamic-free subset.
We therefore evaluate \emph{both} models on Track~2's 912-entry test set: this is the only directly comparable evaluation, since it places both models on identical held-out functions, including the 512 whose reference target is gradual.

\subsection{Model and Training}
\label{sec:llm-training}

\paragraph{Base model.}
We fine-tune \texttt{Qwen2.5-Coder-7B}~\cite{qwen25coder} (the base variant, not instruct) as the foundation model.
This choice reflects three considerations.
First, the Qwen2.5-Coder technical report~\cite{qwen25coder} reports that this model matches or exceeds DeepSeek-Coder-7B-Base~\cite{deepseekcoder} and StarCoder2-7B~\cite{starcoder2} across standard code benchmarks while remaining single-GPU deployable.
Second, Qwen2.5-Coder is pre-trained on over 5.5~T tokens spanning 92 programming languages, including Elixir, a coverage criterion that excludes some alternatives whose Elixir presence is undocumented.
Third, the base variant (rather than the instruction-tuned variant) is more suitable for structured completion tasks: we do not need conversational scaffolding, and starting from a base model avoids fighting habits introduced by chat-format training.

\paragraph{Parameter-efficient fine-tuning.}
At 7~B parameters the model cannot be fully fine-tuned on a single GPU within reasonable time, and the supervised dataset is too small to benefit from full fine-tuning regardless.
We therefore apply QLoRA~\cite{qlora}: the base model is loaded in 4-bit NormalFloat (NF4) quantisation with double-quantisation enabled, and a Low-Rank Adaptation (LoRA)~\cite{lora} layer is attached to all seven linear sub-modules of every transformer block (\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj}, \texttt{gate\_proj}, \texttt{up\_proj}, \texttt{down\_proj}).
The LoRA rank is 32 with $\alpha = 64$ and a dropout of 0.05, giving roughly 80~M trainable parameters out of the 7~B base.

\paragraph{Training configuration.}
Both tracks are trained with an \emph{identical} configuration so that any difference in the models is attributable to the training data, not the procedure.
Training uses the HuggingFace \texttt{TRL} \texttt{SFTTrainer} with sequence packing at a maximum length of 1{,}024 tokens.
The effective batch size is 16 (per-device batch size 2 with 8 gradient accumulation steps).
The learning rate is $2 \times 10^{-4}$ with cosine decay and a 5\% warmup ratio, weight decay 0.01, and bfloat16 mixed precision.
The optimiser is paged AdamW with 8-bit state, and the best checkpoint by validation loss is retained.
Training runs for two epochs on a single GPU; eval-time batch size is reduced to 1 to avoid out-of-memory during the cross-entropy over the 152{,}064-token vocabulary.

\paragraph{Compute environment.}
All training runs were carried out on the LIP6 Convergence cluster, where each job was allocated through Slurm a single NVIDIA~A100 GPU, 8 CPU cores, and host RAM.
Most runs used a half-GPU MIG slice (the \texttt{a100\_3g.40gb} profile, 40~GB) rather than a full A100; the 4-bit QLoRA configuration keeps the 7~B base model together with its LoRA adapters and optimiser state comfortably within the 40~GB budget, so the full \texttt{a100\_7g.80gb} profile was needed only occasionally, and no run approached its time or memory limit.
The compatibility evaluation, which requires the compiler with the typechecker rather than a GPU, was run separately on a local workstation.
Every label variant (raw gradual, compaction, hedging) is trained with the same procedure, so that any difference between them is attributable to the training targets alone.

\paragraph{Training behaviour.}
Both tracks converge cleanly with no instability.
Track~1 trains on \num{2951} entries and Track~2 on \num{5416} (a 1.8$\times$ larger but noisier set, since Track~2's targets include the gradual annotations, a harder objective to fit).
Consistent with this, Track~2 reaches a lower training loss but a higher best-validation loss, and its validation loss bottoms early and drifts up thereafter; best-checkpoint-by-validation-loss selection guards against this for every model.

\subsection{Evaluation: Set-Theoretic Compatibility}
\label{sec:compatibility-eval}

A trained model is evaluated by comparing each predicted annotation against the accepted reference annotation on held-out test entries.
The question a metric must answer is not whether the prediction is textually identical to the reference, but whether it is a \emph{safe} type for the function: one the reference does not contradict.
This is exactly the judgement the set-theoretic type system already provides, so rather than adopt an external similarity heuristic we evaluate predictions with the typechecker's own type algebra (the \texttt{Descr} module, Chapter~\ref{ch:formalisation}).

\paragraph{Why not exact match.}
The most direct metric is exact-match accuracy: the fraction of test entries on which the predicted annotation string equals the reference string.
This is uninformatively strict for set-theoretic types.
Two annotations that describe the identical set of values, for instance a union written as \texttt{A or B} versus \texttt{B or A}, or a map written with one field ordering versus another, are semantically equal but textually distinct; conversely two annotations may differ in a single atom yet denote entirely different value sets.
A binary string comparison conflates these cases, and, more importantly, it penalises a prediction that is a \emph{sound} answer merely for being less precise than the reference, which is the wrong signal for a migration setting where a safe over-approximation is a success, not a failure.

\paragraph{Compatibility.}
We therefore adopt \emph{compatibility}, computed by the \texttt{Descr.compatible?/2} relation: the gradual-typing consistency judgement of the set-theoretic system itself.
A predicted type is compatible with the reference when, treating \texttt{dynamic()} as a wildcard that may stand for any type, the two can be reconciled: the static (non-gradual) content of the prediction must lie within the type the reference permits, so the prediction never \emph{asserts} a shape the reference forbids.
A compatible prediction is thus a safe annotation for the function.
It may be exactly the reference or strictly more general, the limiting case being \texttt{dynamic()} itself, which is compatible with every reference; both count as compatible, whereas a prediction that commits to a concrete shape the reference excludes does not.
This is the appropriate success criterion for a migration setting: an annotation is acceptable precisely when it does not conflict with the function's true type, even at some cost in precision.

\paragraph{Computation.}
Each prediction and reference is parsed into a \texttt{Descr} value and the two are submitted to \texttt{compatible?/2}; parsing collapses whitespace and union-arm ordering and rewrites any \texttt{|} to \texttt{or} (the model occasionally emits the TypeSpec union symbol out of pretraining habit, though the target system writes unions only as \texttt{or}).
A prediction that fails to parse is counted as not compatible (reported separately as \emph{null}); such cases are rare, below \num{2}\% throughout.

\paragraph{With gradual versus without gradual.}
Both models were evaluated on the common \num{912}-entry test set with greedy decoding under a grammar constraint that restricts output to well-formed set-theoretic types.

The with-gradual model is far more compatible (\num{50.4}\% versus \num{32.8}\%).
The reason is structural: \num{512} of the \num{912} test references are themselves gradual (the deterministic translation resorted to \texttt{dynamic()} for them, Subsection~\ref{sec:approximation-via-dynamic}), and the no-gradual model, trained never to emit \texttt{dynamic()}, cannot supply a compatible answer for a reference that expects one; the with-gradual model can.
Under a metric that credits a \texttt{dynamic()} answer as safe, being \emph{permitted} to produce the gradual type is therefore a direct advantage on exactly the half of the test set the no-gradual model cannot reach.
This settles the two-track question that motivated the design: for compatibility, admitting gradual types dominates, and the remainder of this section takes the with-gradual (both-pass) pool as its base and asks how to make its labels \emph{honest}.

\subsection{Honest Labelling: Compaction and Hedging}
\label{sec:honest-labelling}

The with-gradual model of Table~\ref{tab:llm-twotrack} trains on the raw translated annotations, and those labels carry a systematic dishonesty.
Each reference is a translation of a hand-written \texttt{@spec}, so it may state argument and return types the function's \emph{own code} gives no evidence for: a return arm produced only by an opaque call to another function, or an argument whose type is fixed by the specification but never constrained by the clause patterns, guards, or body.
A model trained to reproduce such a label is being taught to recover information it cannot derive from the input, that is, to memorise the specification.
On the held-out test set this inflates exact matches, but it is precision that cannot survive the actual migration setting, where no specification exists (Chapter~\ref{ch:total-migration}).
We therefore evaluate two label transforms, each applied only to the training targets (the test references are left untouched, so all three variants are scored on identical ground truth), that rewrite a label to what the code can honestly support:

\begin{itemize}
    \item \textbf{Compaction} generalises a shape the prompt does not ground: a struct expansion whose fields are not shown in scope collapses to its open nominal form \texttt{\%\{..., :\_\_struct\_\_ => :"Name"\}}, and an ungrounded plain map or keyword shape to its generic \texttt{open\_map()} or \texttt{\{atom(), term()\}} form.
    \item \textbf{Hedging} replaces with \texttt{dynamic()} exactly the positions the code cannot evidence: a return-union arm with no visible constructor in any clause tail (its value comes only from an opaque call), and an argument position that is a bare variable in every clause, unconstrained by any guard and used in the body only as a pass-through. An argument the body \emph{does} constrain (\texttt{x + 1}, \texttt{x.field}, a \texttt{case} subject) is locally derivable and is left concrete.
\end{itemize}

Because a hedged \texttt{dynamic()} is compatible with any reference, hedging trades reference-exact precision for safety without ever teaching the model to assert what it cannot justify.
Table~\ref{tab:llm-honest} reports compatibility for the raw gradual labels and for each transform, all on the both-pass pool and the common \num{912}-entry test set.

\begin{table}[h]
\centering
\begin{tabular}{lr}
\toprule
\textbf{Training-label transform (both-pass pool)} & \textbf{Compatible} \\
\midrule
Gradual (raw translation)                       & 50.4\% \\
Gradual + compaction                            & 63.8\% \\
Gradual + hedging                               & \textbf{69.2\%} \\
\bottomrule
\end{tabular}
\caption{Compatibility on the common \num{912}-entry test set under the honest-labelling transforms. Hedging denotes hedging of both return arms and argument positions; hedging return arms alone reaches \num{62.3}\%, with argument hedging supplying the remainder.}
\label{tab:llm-honest}

Both transforms lift compatibility substantially over the raw gradual baseline, and hedging is the stronger of the two, reaching \num{69.2}\% against compaction's \num{63.8}\%.
The gain from hedging decomposes cleanly: hedging return arms alone accounts for \num{62.3}\%, and hedging argument positions supplies the rest.
The two transforms are complementary in what they honour, one at the level of shapes and one at the level of positions, but hedging is the more principled: compaction still commits to a (generalised) shape, whereas hedging refuses to commit anywhere the code is silent, which is precisely the property the migration setting requires.
Its cost, a lower reference-exact rate, falls almost entirely on the memorised precision described above and so is precision the migration setting could never have obtained in the first place.

For these reasons we adopt the \textbf{gradual + hedging} model as the basis for full migration (Chapter~\ref{ch:total-migration}): it is the most compatible of the trained variants, and, uniquely among them, its output is honest by construction, committing to a type only where the function's own code justifies it and falling back to \texttt{dynamic()} elsewhere, exactly the behaviour required when no reference annotation exists to memorise.

\subsection{Qualitative Analysis}
\label{sec:llm-qualitative}
\label{sec:qualitative}

Inspecting individual predictions makes the trade-off concrete and exposes where the two metrics (intrinsic distance and extrinsic typecheck) agree and disagree. All examples below are drawn verbatim from the two tracks' outputs on the common test set.

\paragraph{The precision gap in one function.}
The function \texttt{DBConnection.Holder.put\_state/2} has reference type \texttt{(term(), term() -> :ok)}.
Track~1 predicts exactly \texttt{(term(), term() -> :ok)}, an exact match that typechecks.
Track~2 predicts \texttt{(dynamic(), term() -> :ok)}: it also typechecks, but it has replaced the first concrete input with the gradual type where the reference, and Track~1, kept it concrete.
Both predictions count as a typecheck ``pass''; only Track~1's counts as safe-\emph{and}-precise.
This single entry is the overall result in miniature.

\paragraph{Recovering precision the translator lost.}
On targets whose \emph{reference} is gradual, Track~1 frequently supplies a precise type that the deterministic translation could not.
\texttt{Pleroma.Bookmark.destroy/2} has reference \texttt{(dynamic(), dynamic() -> :ok or \{:error, term()\})} (the translator widened both arguments to \texttt{dynamic()} because their types came from unresolved remote types), yet Track~1 predicts \texttt{(integer(), integer() -> :ok or \{:error, :not\_found\})}, which typechecks cleanly and even sharpens the error atom.
The model has effectively reconstructed information the translation discarded, which is why Track~1 still attains 45.0\% safe-and-precise on the with-dynamic subset where exact match against the reference is by definition impossible.

\paragraph{Structural equivalents at $d = 0$.}
Some predictions differ textually from the reference yet describe the identical type, and the structural distance metric correctly scores them perfect.
\texttt{Orbit.Ocs.Parser.TschMessage.\allowbreak get\_delete\_status/1} has reference \texttt{(binary() -> :deleted or :undeleted)}; Track~1 predicts \texttt{(binary() -> :undeleted or :deleted)}, the same union with its two arms written in the opposite order.
Both denote the same value set, the metric assigns $d = 0$, and the prediction typechecks.

\paragraph{Near-misses the typechecker catches.}
A revealing class of cases is rated ``close'' ($d = 1$) by the intrinsic metric but \emph{rejected} by the typechecker, precisely the gap that motivates the extrinsic evaluation.
\texttt{Plausible.Exports.\allowbreak delete\_s3\_export!/1} has reference \texttt{(integer() -> :ok)}; Track~1 predicts \texttt{(binary() -> :ok)}.
Structurally the two are one leaf apart (same arity, same return, a single input swapped), so the distance metric scores $d = 1$; but the function indexes an export by an integer id, so the \texttt{binary()} input draws a type warning and the prediction fails extrinsically.
This is the recurring integer-versus-binary confusion, and it shows that a structurally-close prediction is not necessarily a safe one.

\paragraph{Failures at $d = 3$.}
The clearest failures miss a value the body actually returns, and they fail under both metrics.
\texttt{Pleroma.Web.ActivityPub.Relay.get\_actor/0} has reference \texttt{( -> \%\{:\_\_struct\_\_ => :"Pleroma.User"\} or :nil)} (the function returns either a user struct or \texttt{:nil}), while Track~1 predicts \texttt{( -> \%\{:\_\_struct\_\_ => :"User"\})}, dropping the \texttt{:nil} alternative.
Missing an entire return alternative earns $d = 3$, and the prediction also fails to typecheck, since the body can return \texttt{:nil}.
The codes with non-obvious control flow and struct types remain the dominant source of both intrinsic and extrinsic failures.
