\section{Limitations and Future Work}
\label{sec:future-work}

\paragraph{A compiler under active development.}
The set-theoretic type system targeted in this work ships in a development-branch compiler (Elixir~1.21.0-dev) whose type-checking behaviour is not yet stable, and the translation pipeline depends directly on it.
This coupling produced concrete incompatibilities between the translated annotations and the compiler.
The clearest is an arity mismatch in the \texttt{@assert\_type\_form} assertions the translation emits: for a function declaring specifications at several arities alongside a default-argument clause, the assertion generated for a higher arity could be associated by the compiler with a lower-arity clause, aborting compilation of the whole file; resolving these required repositioning the offending \texttt{@spec}s by hand.
Such mismatches are a property of a young, moving target rather than of the translation itself, so the empirical results reported here are tied to a particular snapshot of the compiler and can be expected to shift as its type checker and its handling of assertions mature.
The same holds for the prediction scores: \texttt{compatible?/2} belongs to the compiler's internal, undocumented \texttt{Descr} module, so the compatibility figures are tied to the same snapshot.

\paragraph{Manual project preparation.}
Constructing and evaluating the corpus was not a fully automated pipeline: a number of projects required manual intervention before they would compile under the custom compiler.
The development-branch Elixir is built against a specific Erlang/OTP release (OTP-28), so projects pinning an older toolchain, or depending on libraries incompatible with it, did not build out of the box; bringing them up required pinning compatible dependency versions and adjusting build settings.
For instance, a project that aliased compilation to \texttt{--warnings-as-errors} turned the typechecker's own warnings into hard failures and had to be relaxed.
These interventions mean the corpus cannot yet be regenerated end-to-end without human effort, and that scaling to a substantially larger project set would demand either more robust automated environment resolution or an accepted loss of coverage.

\paragraph{Scope and range of the corpus.}
The corpus is bounded by what the custom compiler's OTP-28 toolchain can build: projects whose dependencies do not compile under it never enter the dataset, so the results generalise to typecheckable Elixir code rather than to the language's full ecosystem.
It is bounded in \emph{range} as well, by the length filter applied before the split (Subsection~\ref{sec:llm-data-prep}), which discards every entry whose function definition exceeds 2{,}000 characters or whose target annotation exceeds 1{,}000.
The pathological cases it removes---variable-arity functions such as \texttt{Regex.replace/4}, whose translated type expands into a union over every fixed arity the BEAM permits (Chapter~\ref{ch:formalisation})---are therefore absent from both training and test.
The models are neither taught nor asked to produce such types, so the reported accuracies say nothing about them: they characterise prediction only within the length envelope the filter keeps.

A third selection acts at the level of the individual function, and it bears directly on what the prediction results can be taken to show.
An entry exists only because some developer wrote a \texttt{@spec} for that function, and functions that carry one need not resemble those that do not: an author is likelier to annotate a public interface than an internal helper, and likelier still to annotate a function whose type was easy to state.
Both models are therefore trained and evaluated on annotated code, while the motivation for predicting types at all is the unannotated majority.
This gap cannot be closed by the metric used here, since scoring a prediction requires a reference annotation to score it against, and a function without a \texttt{@spec} has none.
Closing it needs the extrinsic measurement described below---compiling predicted annotations back into their projects and counting those the compiler accepts---which is what would establish how far these accuracies carry to the code the models are ultimately meant for.

\paragraph{Scale of the supervised corpus.}
The most consequential limitation of the prediction study is the size of that corpus.
The both-pass pool yields only \num{9888} training examples---small for fine-tuning a language model, and a structural consequence of the setting: an Elixir function enters the pool only if it already carries a TypeSpec and that translation is accepted by both checkers, in a language whose typed-code footprint is far smaller than Python's.
So even though we draw on 383 repositories, we retain far fewer usable examples than comparable Python work.
For scale, the closest study---Mengesha's LLM type prediction on Python~\cite{Nina}---trains on \num{56384} examples drawn from 20 of the 50 repositories in its benchmark, and the standard Python type-inference corpus, ManyTypes4Py~\cite{manytypes4py}, contains more than \num{869000} type annotations across \num{5382} projects.\footnote{These counts are not strictly commensurable---our examples are function-level annotations, whereas Mengesha's and ManyTypes4Py's are variable-level---so this is an order-of-magnitude comparison rather than a like-for-like one.}
Data at this scale plausibly caps the absolute accuracies of Section~\ref{sec:llm-results}, and bears more on the 7~B model---the more data-hungry of the two---than on CodeT5+.
The architecture effect itself, however, is unlikely to be a mere artefact of corpus size: Mengesha's Python study, at roughly six times the data, reports the same ranking, a small encoder--decoder ahead of a 7~B decoder-only model~\cite{Nina}.

\paragraph{Consistency of the reference annotations.}
Beyond their number, the references vary in kind.
They are translations of \texttt{@spec}s written by hand across 383 independently developed repositories, and passing both checkers certifies only that each is \emph{sound} for its own function---not that any two were written at the same level of precision.
One author may declare a return type as \texttt{map()}, another spell out every field of the same shape, and a third leave a position to \texttt{term()}; the translation preserves that spread, and the approximation of unresolved remote types adds more of it, which is why \num{60.3}\% of translated entries carry a \texttt{dynamic()} somewhere (Subsection~\ref{sec:approximation-via-dynamic}).
As a training signal this is a target function that is not merely noisy but inconsistently \emph{granular}: the same code can license annotations at several precisions, all of them accepted.
It also weakens the metric at both ends, since a prediction is penalised for disagreeing with whichever convention its reference happened to follow, while a reference left gradual cannot contradict a prediction at all (Section~\ref{sec:compatibility-eval}).
The remedy is not more hand-written specs but a different source of labels: the typechecker already performs module type inference, deriving a type for each function from its body rather than from a declaration (Subsection~\ref{sec:dialyzer-only}), so a corpus of \emph{compiler-inferred} annotations would be uniform in granularity by construction, being produced by one procedure rather than by hundreds of authors.
Its inference is best-effort, and what it derives for a body it cannot pin down would be correspondingly weak, so such a corpus would trade one kind of imprecision for another---but a systematic kind, whose distribution could be measured once and reported, rather than one inherited unevenly from every repository in the sample.
Rebuilding the supervised corpus that way---and comparing a model trained on inferred labels against one trained on translated human specs---is left to future work, and would also decouple the prediction study from the translation prototype that currently supplies its targets.

\paragraph{What the model comparison does not establish.}
Three further limitations qualify that comparison.
First, the two decodings are not symmetric: Qwen2.5 is grammar-constrained to well-formed types while CodeT5+ is not (Section~\ref{sec:llm-results}), so CodeT5+'s stronger numbers are achieved despite a handicap in output well-formedness, visible in its higher null rate.
Second, each model is trained and evaluated on a single subproject split (salt 42); we do not report variance across splits or seeds, so the point estimates should be read as indicative rather than tightly bounded.
Third, checkpoints are selected by validation cross-entropy, a cheap proxy that need not coincide with the set-theoretic compatibility we ultimately report.
That gap is not hypothetical here: between two rounds differing only in the notation of the types supplied in the prompt, Qwen2.5's best validation loss improved by \num{22}\% while its compatibility fell slightly, and CodeT5+'s loss held constant while its compatibility rose two points (Section~\ref{sec:llm-repro}).
A selection criterion computed directly on compatibility---necessarily on validation data, never on the test set---is left to future work.
Because the two models also differ in architecture, scale, and fine-tuning regime at once, the gap between them is not attributable to any one of the three; isolating the encoder's contribution, for instance by fully fine-tuning a decoder-only model of comparable scale under an otherwise identical regime, remains open (Section~\ref{sec:llm-qualitative}).

\paragraph{Dependency types as context.}
The prompt carries only the type declarations in scope at the function itself, not those of the modules it depends on, so the model is never shown the remote types the translator widened to \texttt{dynamic()}---precisely the positions where the reference annotation is least informative.
Supplying those dependency types as additional context is a natural next step, and one the dataset already has the structure to support, since every annotation is recorded with the project and module it came from.

\paragraph{End-to-end total migration.}
This thesis defines \emph{total migration} as the state in which every function in a project carries a typechecker-accepted Elixir Type, and develops its two ingredients separately: a translation prototype for functions that carry a \texttt{@spec} (Chapter~\ref{ch:implementation}), and fine-tuned models that predict annotations for those that do not (Chapter~\ref{ch:llm-eval}).
Composing the two into an end-to-end migration of a complete, previously-unannotated project is left to future work.
Concretely, such a study would run the full pipeline, namely target discovery of untyped functions, annotation \emph{inference} (translation where a spec exists and prediction where it does not), \emph{injection} of the resulting annotation into the source, and recompilation in the original project context, and would report a \emph{migration rate}: the fraction of previously-untyped functions that become compile-clean and free of type warnings.
The prototype already includes an evaluator for the injection step, which writes a prediction into its function's \texttt{@assert\_type\_form} and recompiles the project; it was not run for the results reported here.
A case study over a handful of projects, with a per-function breakdown of outcomes (clean compile, type warning, or compile failure), would connect the compatibility metric of Section~\ref{sec:compatibility-eval} with extrinsic migration success, testing directly whether compatibility with a reference predicts whether a prediction actually migrates.

\section{Conclusion}

This thesis set out to support the migration of existing Elixir codebases to the language's new set-theoretic type system along the two fronts on which type information is available: translating the types that are already declared as Erlang-style TypeSpecs, and inferring those that are not.
Chapter~\ref{ch:formalisation} formalised both type languages and the translation between them as a set of equations, and extended it to a total translation by approximating the TypeSpec constructs that have no exact counterpart, promoting a field's key type to its smallest supertype among the Elixir key types.
Chapter~\ref{ch:implementation} realised the translation as a prototype, which widens to \texttt{dynamic()} the types it cannot resolve, applied it across 383 repositories to produce \num{23073} translated annotations, and checked them against both Dialyzer and the new typechecker, which return a verdict on \num{22621} of them.

The agreement study found the typechecker to be decisively the stricter analysis: it rejects \num{3835} entries (16.6\%) against Dialyzer's 297 (1.3\%).
It independently warns on 199 of Dialyzer's 297 failing entries (67.0\%); the remaining 98 are not cases where it wrongly accepts a definition Dialyzer soundly rejects, but fall to whole-program analyses it does not perform, to 27 locally-checkable findings it misses (10 of them possibly masked by translation-time \texttt{dynamic()}), and to \texttt{@opaque} violations it does not model.
Its excess warnings are mostly translation residuals, yet a core remains that only it catches: 159 purely static return leaks and 457 genuine dead-clause findings.
The two analyses are therefore complementary, and the \num{18688} annotations both accept form the checker-verified corpus for the second part.

The second part fine-tuned two contrasting models on that corpus, length-filtered and split by subproject into \num{9888} training, \num{3484} validation, and \num{2127} test entries: \texttt{Qwen2.5-Coder-7B}, a decoder-only model adapted with QLoRA, and \texttt{CodeT5+-770M}, an encoder--decoder fine-tuned in full.
Predictions were scored with the type system's own compatibility relation, \texttt{compatible?/2}, which accepts a prediction exactly when the reference does not contradict it, and exact match was reported alongside as an indicator of precision.
On the held-out entries CodeT5+ is compatible on 56.3\% against 35.9\% for Qwen2.5, and matches the reference exactly on 29.5\% against 7.7\%, with roughly a tenth of the parameters and without the grammar constraint Qwen2.5 decodes under.
Because the two models differ in architecture, scale, and fine-tuning regime at once, the comparison does not attribute the gap to any single factor, though the same ranking in a Python type-prediction study at roughly six times the data~\cite{Nina} suggests it is not an artefact of our corpus size.

Taken together, the translation prototype supplies types for the functions that already carry a TypeSpec, and a fine-tuned model can propose types for those that do not.
The predictions, however, were scored against reference annotations rather than compiled into their projects, so whether they carry a real codebase through migration remains to be measured; this is the principal item of future work set out above.
