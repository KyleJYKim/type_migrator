\part{Translating TypeSpecs into Elixir Types}

Existing Elixir code already carries type information---the optional \texttt{@spec} annotations Dialyzer consumes---but written in TypeSpecs, a syntax the new set-theoretic type system does not read.
This part turns those annotations into the new system's types: it formalises both type languages and the translation between them, implements that translation as a prototype over real-world code, and validates the resulting dataset by cross-checking Dialyzer against the new typechecker.
That checker-verified dataset is the supervised signal from which the second part learns.

\chapter{Formalisation}
\label{ch:formalisation}
This chapter provides rigorous type syntax formalisation both TypeSpecs and Elixir Types in order to produce theoretical translation equations.
Our formalisation starts with TypeSpecs syntax from existing TypeSpecs reference~\cite{elixir-typespecs,erlang-typespecs}, which lists not only the basic types but also the built-in types and syntactic sugars.
The syntax specification of Elixir Types is then provided based on the Featherweight Elixir~\cite{duboc2024}.
Finally, we introduce the translation equations and discriminate the types that are not able to be directly translated, which leads us to suggest approximation of translation.

\chapter{Implementation and Analysis}
\label{ch:implementation}
This chapter demonstrates the translation we have formalised in the previous chapter.

We first build a prototype that translates TypeSpecs based on Elixir's abstract syntax tree (AST) and produces Elixir Types in which form customised to be consumed by the new compiler (version 1.21.0-dev).
This prototype also involves collecting and translating user-defined types or remote types that are defined by directives \texttt{@type}, \texttt{@opaque}, and \texttt{@typep} in order to expand them in TypeSpecs.
The following section runs Dialyzer and the new compiler's typechecker on various codebases that are used in the real world. Which process produces the raw dataset.
Then, we analyse the raw dataset, examining the warning messages and success rate with quality.
The final analysis eventually helps building a feasible dataset that we can use for applying to large language models in the next part.

\part{Inferring Elixir Types with Large Language Models}

The translation pipeline of Chapter~\ref{ch:formalisation} converts existing TypeSpec annotations into Elixir Types, and the analysis of Chapter~\ref{ch:implementation} characterises how the \num{23073} translated annotations are analysed under the two checkers: \num{18688} (81.0\%) are accepted by both, while the rest are dominated by translation-time \texttt{dynamic()} approximation and the typechecker's conservative module-local inference, with only a small residue of genuine type errors.
Yet translation only reaches functions that \emph{already} carry TypeSpecs.
Most production Elixir code carries none: in the application code of our corpus, only \num{15694} \texttt{@spec} annotations accompany \num{119901} \texttt{def} and \texttt{defp} clauses, so the large majority of functions go unspec'd.
Developers omit the optional \texttt{@spec} directives; Dialyzer still analyses these functions by inferring success typings~\cite{lindahl2006practical}, but with no declared contract there is no developer's intended type to hold the body to.
A complete migration to the typed environment is therefore not addressed by translation alone; the remaining, dominant, fraction of the codebase requires that an annotation be \emph{inferred}.

The chapters that follow investigate whether a large language model fine-tuned on the corpus of translated, typechecker-accepted annotations can supply such inferences with enough fidelity to drive the migration.
The supervised signal is the by-product of the agreement study (Subsection~\ref{sec:downstream-implications}): the \num{18688} \emph{both-pass} entries that both tools accept, which after a length filter form the training corpus detailed in Subsection~\ref{sec:llm-data-prep}.
Each entry pairs a function definition with an Elixir Type annotation the typechecker accepts as consistent with that definition, and the supervised task is to recover that annotation from the definition.

This prediction task is an unusual one for a language model, distinctive in three ways.
First, the target type system is set-theoretic: a prediction must produce unions, intersections, and constructor-shaped types with explicit field information, not the class names of a nominal type system.
Second, the task is type \emph{generation}, not type \emph{correction}: unlike the correction setting of~\cite{Nina}, in which a possibly-incorrect type is supplied and refined, the model here is given only the function definition and must produce the annotation from scratch.
Third, and most sharply, the target notation is itself unfamiliar to the models: the set-theoretic Elixir Types are emitted by an in-development compiler and barely appear in any public corpus, so the notation is essentially unseen in pretraining.
A code model can lean on a mature type language such as Python's or TypeScript's---which it has already absorbed during pretraining---and learn only \emph{when} to apply it; here it must instead learn the notation itself, its constructors, its unions written as \texttt{or}, and its \texttt{dynamic()}, from the supervised data.

We pursue two model families in parallel on this both-pass pool---a large decoder-only model and a much smaller encoder--decoder, fine-tuned on the same annotations---and compare how well each architecture supports the prediction task.
